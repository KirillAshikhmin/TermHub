## Что удивило (расхождения и ловушки)

1. **Лента в таб-баре — не пятый таб.** CLAUDE.md пишет «таб «Лента» последним перед ⋮»; в коде (`ui.ts:477-494`) это кнопка `.th-holotab__feed` ВНУТРИ плашки «Терминал». Переключатель «терминал ↔ чат» придётся проектировать заново (кнопка внутри ссылки: `preventDefault+stopPropagation`, иначе клик = переход на терминал).
2. **`mountFeed` монтирует собственную шапку сессии** (`mountSessionBar`, `renderHoloBar`, `wireToolbar`) внутри вкладки; терминальная вкладка делает то же самостоятельно (`mountSessionTabs`). Чат как «вид» терминальной вкладки либо вынесет это в общий каркас, либо задвоит полосы.
3. **Пока открыта лента, терминальный view той же сессии жив** (workspace кэширует views) — у сессии уже есть TermChannel; встроенный терминал в чате = второй pty-клиент и борьба за размер окна tmux (`claim`).
4. **`remote.ts:336` ветка `sfeed` монтирует `mountFeed` напрямую**, но при живом `transport` перехватывается workspace (main.ts:104) — ветка по сути мёртвая; новый маршрут чата нужно добавлять в `routeWorkspace` и `parseRoute`, не в `remote.render`.
5. **Нет метода «послать клавиши / снять экран» ни в Transport, ни в агенте вне `Link`.** Всё придётся делать с нуля на двух проводах (LAN-маршрут + кадр ≥48 + права: `write` для send-keys, чтение экрана — как у ленты, но НЕ по умолчанию: `default: break` в гейте relay пропустит неизвестный кадр гостю). Экран панели может содержать секреты — чтение экрана гостю без `write` решать явно.
6. **Ответ ленты в relay не коррелируется по id** (`pendingFeed`, один в полёте, `feedOwed`) — копировать эту схему для новых запросов опасно; `fileOp` с `id` надёжнее. Если запрос «экран панели» будет опрашиваться раз в 1-3 с, нужен id или отдельный тип ответа (урок ADR 0030).
7. **Ввод в терминал и `\n`**: `\n` = submit в Claude Code; перенос — `\x1b\r` (`doCompose`, `SEND_KEYS.shiftEnter`). Отправка многострочного текста `send-keys -H` по байтам — корректна для tmux, но для TUI без bracketed paste каждое `\x1b\r` может истолковываться как Alt+Enter; проверь живьём, не в Chrome (правило «не гонять в Chrome»; живое — только изолированные tmux-сокеты).
8. **Результаты инструментов отбрасываются на стороне агента намеренно** (`toolUseResult`, Codex `*_output`) и экономят страницы (на Codex треть ленты — пустое мышление). Подтягивание вывода раздует страницы: нужен отдельный лимит и, вероятно, «ленивая подкачка вывода по курсору/`tool_use_id`» вместо вложения в страницу.
9. **Пары tool_use/tool_result разнесены по строкам** и могут оказаться на разных страницах; страница уже бывает шире `limit` из-за многоблочных строк — связку делать на клиенте по id либо отдельным запросом.
10. **`ARG_LIMIT` = 400** (не 200, как в CLAUDE.md); подписи инструментов режутся до первой строки.
11. **Версия агента:** Claude — в `SessionInfo.command` (голая версия) и в реестре `~/.claude/sessions/<pid>.json` (`version`, `status`), в строках транскрипта (`version`, `message.model`). Определитель их не отдаёт. Реестр содержит ещё `status` — потенциальный дешёвый источник «думает/ждёт» без чтения экрана (формат значений не проверен). Версия Codex в `command` не видна.
12. **`DiagInfo` (api.ts:219) не объявляет `caps`**, хотя `/api/diag` его отдаёт (`server.ts:563`); в relay диагностика строится на клиенте без `/api/diag` — счётчик «неузнанных экранов» должен жить на клиенте, иначе пропадёт на relay.
