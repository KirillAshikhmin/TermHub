# 06 — Снять DCS-обёртку и завести шов с настоящим tmux

**Требования:** R01, R02, R09, R10, R11, D07
**Blocked by:** 01, 02, 03

**Волна:** 5
**Status:** ready

## Что должно заработать

Control mode должен наконец включаться на живом tmux. Сейчас он не включается ни разу:
поток `-CC` начинается с DCS-обёртки iTerm2, склеенной с первым `%begin`
(`\x1bP1000p%begin <ts> <id> <flags>`), разбор её не снимает, приветственный блок не
опознаётся, номер команды остаётся неизвестным — и каждое подключение через пару секунд
скатывается на прежний `tmux attach`. Снимка нет, история не листается, статусная строка
tmux на месте: весь этап на живой машине не даёт ничего.

Слепая приёмка сняла это с настоящего tmux 3.7b:

```
[109ms]  control protocol answers, waiting for the first block number
[2110ms] control mode unavailable (no block number in 10000 ms of notifications), using tmux attach
[2115ms] READY mode=attach ;  snapshot bytes=0
```

Тот же разбор на потоке одиночного `-C`, где обёртки нет, даёт номер блока сразу.

## Почему это не поймали тесты

Приветствие в тестах подделано вручную, без обёртки: `GREETING = '%begin 1 0 1\n%end 1 0 1\n'`.
Ни одного теста над настоящим потоком `-CC` в наборе нет. Живые tmux-тесты проекта зелёные
потому, что проверяют эхо и размер, а это работает и в режиме отката.

## Из брифа, дословно

> «`tmux -CC attach` вместо `tmux attach`»

> «разбор строчного протокола и разэкранирование октальных последовательностей»

> «История листается там, где раньше не листалось ничего»

## Критерии приёмки

- [ ] Разбор снимает DCS-обёртку в начале потока и опознаёт склеенный с ней первый `%begin`
- [ ] Завершающая последовательность DCS в конце потока не ломает разбор и не выходит наружу
      мусорным событием
- [ ] Обёртка снимается только там, где она есть: поток одиночного `-C` и поток без обёртки
      разбираются как раньше
- [ ] Есть тест на реальное начало потока, снятое с живого tmux, а не на подделанное
      приветствие; на прежнем коде он красный
- [ ] **Есть живой шов:** тест, который поднимает настоящий tmux на изолированном сокете
      (`-L termhub-test-<уникальное>` с `kill-server` в teardown), подключается через
      `session-link`, и утверждает, что выбран именно control mode и что снимок непустой.
      Этот тест — единственная защита от повторения такого дефекта, и он должен падать,
      если разбор снова перестанет опознавать начало потока
- [ ] Живой тест не трогает дефолтный tmux-сервер и не зависит от сессий пользователя
- [ ] Шапка `packages/web/src/touch-scroll.ts` больше не утверждает, что `tmux attach`
      держит терминал в альтернативном экране всю сессию как основной путь: после этого
      этапа основной путь другой, а комментарий рядом в `term.ts` уже говорит обратное
- [ ] Прежние тесты разбора остаются зелёными, типы чисты
