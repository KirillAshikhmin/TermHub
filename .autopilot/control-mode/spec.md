# Спецификация: этап 1 — control mode вместо attach

Режим прогона: полуавтомат · глубина: максимальная. Решения архитектуры приняты на прогоне
`own-terminal-mosh-ux` и здесь не переоткрываются: ADR `0013`–`0018`. Это первый этап
дорожной карты из `docs/terminal-and-agents.ru.md`.

---

## Задача

Терминал подключается к сессии через `tmux attach`. Эта команда первым же байтом шлёт
`ESC[?1049h` и держит клиента в альтернативном экране до самого detach. У альтернативного
экрана нет истории по стандарту, поэтому:

- прокрутка в сессии с агентом не работает локально, каждый шаг идёт в copy-mode по сети;
- статусная строка tmux занимает строку экрана телефона, где она не нужна;
- каждое переподключение — полная перерисовка экрана, а не продолжение.

## Решение

Терминал подключается через `tmux -CC attach` — control mode. В нём tmux не рисует экран,
а отдаёт содержимое панелей строчным протоколом; UI рисует клиент. Альтернативный экран не
приходит, статусная строка не приходит, подключение стоит десятки байт.

Ввод идёт командой `send-keys -H`, размер окна — `refresh-client -C`, первый экран и
восстановление — `capture-pane -p -e -S -N`. Всё это команды в stdin того же клиента,
второго процесса tmux не появляется.

Если control mode не поднялся, терминал работает через прежний `tmux attach`. Решение
принимается один раз при подключении и пишет причину в лог.

## Что измерено на живом tmux 3.7b

К замерам прошлого прогона (`docs/terminal-and-agents.ru.md`, раздел «Что измерено»)
добавлены четыре, сделанные для этого этапа.

| Что проверено | Результат |
|---|---|
| Начало потока `-CC` | первая строка приходит с DCS-обёрткой iTerm2, склеенной с первым `%begin`: `\x1bP1000p%begin <ts> <id> <flags>`; у одиночного `-C` обёртки нет |
| Команда через stdin control-клиента | ответ приходит блоком `%begin <ts> <id> <flags>` … `%end <ts> <id> <flags>`; `<id>` растёт и позволяет сопоставить ответ с командой |
| `display-message -p "#{pane_id} #{window_id} #{alternate_on}"` | отвечает `%0 @0 0` — активная панель, её окно и признак альтернативного экрана достаются одной командой |
| `capture-pane -p -e -S -N` через control-клиента | работает, содержимое приходит внутри блока `%begin`/`%end`; отдельный процесс tmux не нужен |
| Смена активного окна | приходят `%session-window-changed $0 @1`, `%window-add @1`, `%window-renamed @1 tmux` |
| `refresh-client -C` | принимает оба написания: `90x28` и `90,28`; выбираем `WxH` — оно старше и работает на большем числе сборок |
| Формат экранирования в `%output` | экранируются только управляющие байты и сам обратный слэш, тремя восьмеричными цифрами: `\015` (CR), `\012` (LF), `\033` (ESC), `\134` (`\`). Многобайтовый UTF-8 проходит сырым: кириллица и эмодзи не экранируются |
| Вход приложения в альтернативный экран | приходит внутри `%output` как `\033[?1049h`; отдельного уведомления tmux не шлёт, `%layout-change` при этом нет |

### Блок 1. Подключение (R01, R08, G01, R11)

| Измерение | Решение |
|---|---|
| Первый запуск | Первое подключение: control mode отдаёт пустой экран, поэтому клиент сначала просит срез, потом включает поток |
| Пусто | Сессия только создана, вывода нет: экран пуст, приглашение придёт первым `%output` |

| Измерение | Решение |
|---|---|
| Первый запуск | До первого `%begin` поток считается неготовым; ничего не рисуем |
| Пусто | Пустой `%output` (нулевая длина) — валиден, ничего не пишем в экран |

## Решения по реализации

### §1. Одна точка замены на три пути

`attachTerminal` в `bridge.ts` — единственное место, где сегодня спавнится `tmux attach`.
Её используют оба пути: LAN через `wireTerminalWs` и relay через `relay-link.ts`, а
CLI-клиент ходит через relay-фреймы к тому же коду. Поэтому замена делается там и покрывает
все три пути сразу.

**Почему так.** Отдельные реализации для LAN и relay разошлись бы в первый же месяц, а
CLI остался бы на старом пути молча.

### §2. Два новых модуля с чистой границей

Первая строка потока приходит внутри DCS-обёртки iTerm2 (`\x1bP1000p`), склеенной с первым
`%begin`. Разбор обязан её снять: иначе приветственный блок не опознаётся, номер команды
остаётся неизвестным, и подключение уходит в откат при живом control mode (`D07`).

Экранирование, которое разбирает `parse`: три восьмеричные цифры после обратного слэша
(`\015`, `\033`, `\134`), и экранируются только управляющие байты и сам слэш —
многобайтовый UTF-8 приходит сырым. Проверено пробой.

- **`control-protocol`** — разбор строчного протокола. `parse(chunk) -> Event[]` возвращает
  события `output` (панель и байты), `block` (ответ на команду по её номеру), `notification`
  (смена окна, панели, выход), `error`. `escapeInput(bytes) -> string` превращает байты в
  аргументы `send-keys -H`. Модуль не знает ни про tmux-процесс, ни про сеть, ни про DOM.
- **`session-link`** — жизненный цикл control-клиента: `open(session, opts) -> Link`,
  `Link.write(bytes)`, `Link.resize(cols, rows)`, `Link.snapshot(lines)`, `Link.dispose()`,
  плюс `pause`/`resume` для обратного давления. Он выбирает режим, держит очередь команд,
  сопоставляет ответы по номеру и следит за активной панелью.

`bridge.ts` остаётся обвязкой WebSocket и сохраняет свой нынешний контракт
`TerminalHandle`, расширенный двумя членами: `snapshot(lines)` и сигнал о смене состояния
альтернативного экрана.

**Почему так.** Шов, названный в дорожной карте, должен существовать в коде, иначе разбор
протокола окажется внутри обработчика WebSocket и проверяться будет только через живой tmux.

### §3. Готовность определяется первым блоком, а не тишиной

После спавна `tmux -CC attach` готовность к командам даёт **первый блок**: до него неизвестен
номер, которым адресуется ответ. `%session-changed` — признак живого протокола, но не
готовности (`D03`). Клиент считается поднявшимся, когда пришёл первый блок **и** разобран
ответ `display-message` с активной панелью. Поводов
для отката четыре: за 2 секунды не пришло ничего, а при живых уведомлениях за 10 секунд не
пришёл первый блок; процесс завершился; в потоке `%error`; ответ про активную панель не
разобран (`D02`). Последний повод защитный: без активной панели
нечем фильтровать чужой вывод, и рисовать смесь двух панелей хуже, чем работать по-старому.

**Почему так.** Определять поддержку по версии tmux хрупко: сборки различаются, а строка
версии врёт при патчах дистрибутива. Первый блок — прямое доказательство, что протокол
работает на этой машине.

### §4. Выбор режима: настройка агента, просьба клиента, автоматический откат

Порядок решения, один раз при открытии терминала:

1. Конфиг агента `terminalMode` — `"control"`, `"attach"` или отсутствует (тогда `control`).
   Значение `"attach"` запрещает control mode целиком.
2. Просьба клиента едет **первым кадром, которым клиент открывает терминал**: в LAN это
   RESIZE, через relay — OPEN, потому что терминал relay создаётся на OPEN и к RESIZE
   решение уже принято (`D04`). На реконнекте живого канала повторяется тот же снимок
   просьбы: смена режима ждёт нового открытия терминала. Клиент может попросить `attach`;
   попросить `control` там, где агент его запретил, нельзя.
3. Проверка готовности (§3). Отказ — откат на `attach` с причиной в лог.

Выбранный режим возвращается клиенту, чтобы интерфейс показывал, что работает сейчас.

**Почему так.** Пользователь выбрал ручку и в конфиге, и в интерфейсе (вопрос 1). Конфиг
старше просьбы клиента: это машина владельца, и запрет на ней должен быть окончательным.

### §5. Активная панель известна и отслеживается

Сразу после готовности `session-link` спрашивает
`display-message -p "#{pane_id} #{window_id} #{alternate_on}"` — одна команда даёт активную
панель, её окно и состояние альтернативного экрана. Дальше он слушает уведомления смены окна
и панели и переспрашивает при каждой. `%output` не активной панели отбрасывается.

**Почему так.** В control mode tmux отдаёт вывод всех панелей сессии. Без фильтра экран
телефона смешает две панели, и это будет выглядеть как порча вывода.

### §6. Первый экран и снимок — командой в том же клиенте

`capture-pane -p -e -S -N` уходит той же дорогой, что остальные команды, и приходит блоком
`%begin`/`%end`. Второго процесса tmux не появляется.

**Сколько строк.** Глубину задаёт вызывающий, значение по умолчанию — 200 строк. Этого
хватает, чтобы сразу было что листать, и это около 18 КБ по замеру 89 байт на строку.
Просить всю историю при каждом открытии нельзя: 50 000 строк — это 4.4 МБ на каждое
подключение, и по relay они пойдут по сети.

**Почему так.** Проверено пробой. Отдельный `execFile` — лишний процесс на каждое открытие
терминала и второй путь к тем же данным.

### §7. Ввод пачками, а не по символу

Байты ввода копятся в очереди и уходят одной командой `send-keys -H` на цикл событий.
Порядок сохраняется, потому что очередь одна. Размер окна уходит как `refresh-client -C WxH`:
оба написания работают на 3.7b, но `WxH` старше и встречается в большем числе сборок.

**Почему так.** Команда на каждый символ превращает быстрый набор в поток команд tmux с
ответами `%begin`/`%end` на каждую; пачка стоит столько же, сколько одна команда.

### §8. Пометка альтернативного экрана

Состояние берётся из `display-message` при подключении и при каждой смене активного окна
или панели. Между этими моментами оно обновляется разбором потока активной панели:
`\033[?1049h` — вход, `\033[?1049l` — выход. Отдельного уведомления tmux не шлёт, это
проверено пробой. Клиенту состояние отправляется отдельным кадром состояния терминала.

**Почему так.** Пользователь должен отличать «история кончилась» от «в этом приложении
истории не бывает». Кадр новый, и по правилу совместимости (`docs/adr/0018`) клиент,
который его не знает, обязан его пропустить — декодер кадров это уже позволяет.

### §9. Пресет Codex получает `--no-alt-screen`

В список аргументов пресета добавляется флаг. Он существует у Codex и означает ровно
«inline, сохраняя scrollback».

**Почему так.** Без него следующая версия Codex может вернуть альтернативный экран по
умолчанию, и история в его сессиях исчезнет без единой строки в коде TermHub.

### §10. Тесты

- `control-protocol.parse` — чистая функция: разбор `%output`, разэкранирование, склейка
  разорванной строки, блоки `%begin`/`%end`, неизвестные уведомления, битые данные.
- `escapeInput` — байты в аргументы `send-keys -H`, включая управляющие и многобайтовые.
- `session-link` — на поддельном процессе: выбор режима, откат по таймауту, откат по
  `%error`, фильтр чужой панели, смена активного окна, очередь ввода, снимок.
- Прежние тесты остаются зелёными; тесты, которые подменяли `attachTerminal`, продолжают
  работать через тот же контракт.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `control-protocol` | разбором строк control mode и кодированием ввода | `parse(chunk) -> Event[]`, `escapeInput(bytes) -> string` | октальное экранирование, склейку кусков, состояние блоков |
| `session-link` | жизненным циклом control-клиента, выбором режима, активной панелью, очередью команд | `open(session, opts) -> Link`, `write`, `resize`, `snapshot`, `pause`, `resume`, `dispose`, `mode` | спавн процесса, откат, сопоставление ответов по номеру |
| `bridge` | обвязкой WebSocket поверх `TerminalHandle` | нынешние `attachTerminal` и `wireTerminalWs` | какой дорогой добыты байты |

**Швы для тестов — два:** `control-protocol` целиком (чистые функции) и `session-link`
(на поддельном процессе). Остальное проверяется существующими швами проекта.
