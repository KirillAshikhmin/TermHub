# Спецификация: лента агента из транскрипта

## Задача

В сессии Claude Code экрана-истории нет: приложение занимает альтернативный экран, и всё,
что выше текущего кадра, недоступно — листать нечего. У Codex история есть, но она такая
же, как в терминале: перемешана с рамками, спиннерами и перерисовками.

При этом оба агента ведут на диске полную запись беседы. Первый этап научился отвечать,
какой агент работает в панели и где лежит файл его беседы. Этот этап должен превратить
файл в ленту: читаемую последовательность реплик, одинаковую для обоих агентов, и довести
её до клиента обоими путями — по LAN и через relay.

## Решение

Агент отдаёт по запросу **ленту сессии**: список записей от старых к новым, с курсором для
подкачки назад и вперёд. Запись одна и та же для Claude и Codex — различий форматов
снаружи не видно.

Что попадает в ленту (решение пользователя, G01):

- реплики человека и агента — целиком;
- мышление — отдельным видом записи, показывать его решает экран;
- вызов инструмента — **одной строкой** «что сделал»: имя инструмента и короткий аргумент,
  без вывода;
- служебные вехи — сжатие контекста, прерывание, ошибка запроса — отдельным видом.

Экрана в этом прогоне нет: он третий этап. Здесь строится то, что экран будет читать.

Совместимость — объявлением возможностей (ADR 0018): клиент называет, что понимает, агент
отвечает тем, что умеет; лента включается только при совпадении. Клиент, который про ленту
не знает, продолжает работать как раньше; агент, который её не умеет, не ломает клиент.

## Решения по реализации

**§1. Запись ленты.** Одна форма для обоих агентов:

```ts
interface FeedEntry {
  /** Стабильный идентификатор: `uuid` у Claude, `payload.id` или `ordinal` у Codex.
   *  Нет ни того ни другого — смещение строки в байтах, оно же начало курсора: файлы
   *  только дописываются, поэтому смещение строки не меняется никогда. */
  id: string;
  /** Момент, epoch ms. На живых данных есть у каждой записи обоих агентов (замер
   *  14.09.2026: 1834 записи Claude и 15 500 записей Codex — `timestamp` у всех).
   *  Нет — берётся от предыдущей записи окна, а для первой в окне — от следующей, у
   *  которой он есть; нет ни у одной — 0, и экран показывает запись без времени. */
  at: number;
  kind: 'human' | 'agent' | 'thinking' | 'tool' | 'note';
  /** Текст записи. У `tool` — одна строка «что сделал». У `note` — подробность из
   *  источника (текст ошибки), либо пустая строка: саму веху называет `note`. */
  text: string;
  /** Имя инструмента — только у `kind: 'tool'`. */
  tool?: string;
  /** Что за веха — только у `kind: 'note'`. Код, а не фраза: слова подбирает экран,
   *  у него оба словаря (ru+en), у агента ни одного. */
  note?: 'compacted' | 'interrupted' | 'error' | 'chain';
  /** Ветка подагента — только у Claude (`isSidechain`, имя из `agentName`). У Codex
   *  вложенные потоки лежат отдельными файлами и в корневой не попадают вовсе. */
  branch?: string;
  /** Текст обрезан по пределу записи. */
  truncated?: true;
  /** Курсор этой записи — «<inode>:<offset>», та же форма, что принимают `before`/`after`/
   *  `around`. Ставит его страница; `parseLine` не ставит, потому что разбирает строку в
   *  отрыве от файла и признака файла не знает (D03). */
  cursor?: string;
}
```

Почему так: экран третьего этапа должен уметь скрыть мышление и свернуть инструменты, не
зная, чей это формат; всё, что для этого нужно, — вид записи и текст.

**§2. Откуда что берётся.**

| Вид | Claude (`.jsonl`) | Codex (rollout) |
|---|---|---|
| `human` | `type: user`, блоки `text`/строка, кроме `isMeta` и `toolUseResult` | `response_item` → `message`, `role: user` |
| `agent` | `type: assistant`, блок `text` | `response_item` → `message`, `role: assistant` |
| `thinking` | блок `thinking` | `response_item` → `reasoning` |
| `tool` | блок `tool_use`: имя + первый значимый аргумент | `function_call` / `custom_tool_call`: имя + аргумент |
| `note` | `isCompactSummary`, `isApiErrorMessage`, `interruptedMessageId` | `compacted`, `event_msg` → `error` |
| — (не берём) | `attachment`, `file-history-*`, `queue-operation`, `last-prompt`, `ai-title`, `agent-name`, `mode`, `permission-mode`, `atis-latch`, блоки `tool_result` | `token_usage_record`, `event_msg` → `token_count`, `turn_context`, `world_state`, `message` с `role: developer` |

Служебные виды записей у Claude перечислены явным списком «что берём», а не «что
выбрасываем»: типов там полтора десятка и их число растёт с каждой версией, а виды ленты
фиксированы решением пользователя.

**§3. Строка «что сделал».** Имя инструмента плюс аргумент, который человек узнаёт:
путь файла (`file_path`, `path`, `notebook_path`), команда (`command`), образец поиска
(`pattern`), адрес (`url`), запрос подагента (`description`). Ничего из перечисленного нет
— одно имя инструмента.

Уточнение по замеру (D02): предел аргумента — **400 знаков**, и у Codex подпись собирается из
команд скрипта, а не из первого аргумента. Прежние «первый аргумент» и «200 знаков» были
догадкой, и она не выдержала живых данных: вызов Codex приходит строкой JavaScript, которая
оборачивает настоящую команду (`await tools.exec_command({cmd:"…"})`), так что «первый
аргумент» — это обёртка, а не дело. После разбора медиана команды 140 знаков, 75-й процентиль
295; при пределе 200 обрезано 36,3 % подписей Codex и 58,5 % Claude, при 400 — 14,9 % и 36,4 %.

Поле `cursor` добавлено по находке второй слепой приёмки (D03): без него история 9.1
формально выполнена, а на деле не работает — экран держит в руках **запись**, найденную
поиском, а `around` принимает только курсор, и на `id` записи отвечает `cursor-stale`.
Адресовать середину страницы было нечем: §4 отдаёт курсоры только её краям.

**§4. Чтение файла и курсор.** Файлы обоих агентов — построчный JSON и только дописываются.
Поэтому курсор — это **смещение в байтах** плюс признак файла:

```
cursor = "<inode>:<offset>"
```

Признак файла нужен, чтобы курсор не пережил смену сессии в панели: `resolve` может начать
показывать другой файл, и старое смещение попало бы в середину чужой беседы. Не совпал —
отказ `cursor-stale`, клиент берёт хвост заново.

Три режима запроса, все возвращают записи в порядке от старых к новым:

| Запрос | Что отдаёт |
|---|---|
| без курсора | последние `limit` записей (хвост) |
| `before=<cursor>` | `limit` записей, кончающихся этим смещением |
| `after=<cursor>` | всё, что появилось после смещения, не больше `limit` |

Четвёртый режим — `around=<cursor>`: половина `limit` до записи и половина после. Он нужен
экрану третьего этапа для «перехода к месту»: найдя запись поиском, он должен показать её в
окружении, а не перематывать ленту с хвоста. Стоит он того же одного чтения, что и хвост,
и добавить его потом значило бы править протокол.

Хвост и `before` читаются окном, растущим назад от известного смещения: 256 КиБ, при
нехватке записей окно удваивается до 4 МиБ. Первая строка окна почти всегда обрезана — она
отбрасывается, кроме случая, когда окно начинается с начала файла. `after` и `around`
читают вперёд от смещения тем же окном.

Курсор адресует **файл и место в нём**, поэтому он же переносит ленту через границу файлов
цепочки (§7): дойдя до начала дочернего файла, `before` отдаёт `bof: true` для него, а
следующая страница приходит уже с `inode` родителя. `cursor-stale` означает ровно одно —
такого `inode` нет ни в текущем файле, ни в его цепочке.

**§5. Пределы.** `limit` по умолчанию 200, максимум 1000. Ответ не больше 1 МиБ: набрав его,
чтение останавливается и отдаёт, что успело, — курсор покажет, откуда продолжить. Текст
записи режется по **64 КиБ** с пометкой `truncated`. Пределы одни на оба транспорта:
relay-кадр и HTTP-ответ несут один и тот же JSON.

Число 64 КиБ — не догадка (D01): на 11 643 репликах и мышлениях из транскриптов владельца
медиана 7 байт, 99-й процентиль 7,8 КиБ, максимум 90 КБ. Прежний предел 8 КиБ резал 0,94 %
записей, а требование пользователя (G01) говорит «реплики человека и агента — целиком».
При 64 КиБ режется 0,02 % — две записи из 11 643, и обе заведомо не реплики, а вставленные
простыни. Потолок ответа при этом не меняется: страница из длинных записей просто короче.

**§6. Ответ.**

```ts
type FeedResult =
  | { ok: true; agent: 'claude' | 'codex'; entries: FeedEntry[];
      /** Курсоры краёв отданного куска. */
      head: string; tail: string;
      /** Достигнуто начало файла / конец файла. */
      bof: boolean; eof: boolean;
      /** Оба поля — как их отдал определитель первого этапа (`resolve`), без пересчёта:
       *  `complete` — беседа целиком, `live` — работает ли ещё писавший её процесс. */
      complete: boolean; live: boolean;
      /** Сколько строк пропущено как неразобранные. */
      skipped: number }
  | { ok: false; reason: 'no-agent' | 'unknown-format' | 'no-transcript' | 'lookup-failed' | 'cursor-stale';
      detail: string };
```

Причины отказа — те же четыре, что у определителя, плюс `cursor-stale`. Новых слов для
старых причин не вводим: их уже знает агент и будет знать экран.

**§7. Цепочка Codex.** У корневого потока может быть `forked_from_id` — тогда начало беседы
лежит в другом файле. Пользователь решил: лента панели — вся беседа, цена принята. Значит
при `bof` лента продолжается в файле-родителе: он ищется по `threadId` в именах файлов
`~/.codex/sessions/**` (проверено на живых данных: у 20 из 20 форкнутых потоков родитель
находится именно так). Место склейки помечается записью `note`, чтобы разрыв во времени не
читался как потеря. Глубина цепочки ограничена 10 файлами, дальше `bof: true` — ограничение
против цикла в чужих данных, а не против длинной беседы.

Уточнение по находке ревью 14.09.2026: отвечать на этом пределе `bof: false` нельзя — курсор
дальше не двигается, и клиент листает одну и ту же веху бесконечно, то есть попадает ровно в
цикл, ради которого предел и введён. Но и молча выдавать предохранитель за начало беседы не
нужно: страница отдаёт `bof: true` **и** веху `note: 'chain'` на месте обрыва. Клиент
останавливается, а причина остановки названа.

Цепочка редка и на сегодняшних данных владельца недостижима: `forked_from_id` есть у 51
вложенного потока из 248 и **ни у одного** из 80 корневых, а лента строится только по
корневому. Строим всё равно — требование пользователя прямое, механизм проверен, а шов
`readFeed` позволяет проверить его на подложенной паре файлов, не дожидаясь живого случая.

Отдельного «продолжения» у Codex нет: в `session_meta` всех 328 файлов владельца есть
`forked_from_id` и `subagent_history_start_ordinal`, и ни одного поля со смыслом «эта беседа
продолжает вон ту». Значит для Codex цепочка — это ровно форк, и другого случая не бывает.

У Claude цепочки нет по D01 прошлого прогона: продолжение копирует беседу целиком.

**§8. Адресация.** Клиент знает имя сессии, а не адрес панели, поэтому запрос принимает
**имя сессии**; активную панель агент находит сам (`display-message -p`) и передаёт
определителю. Это же делает проверку прав гостя той самой, что в `doList`/`doOpen`.

**§9. Транспорты.**

- LAN: `GET /api/feed?session=<имя>&limit=&before=&after=` → JSON из §6, под той же
  cookie-авторизацией и проверкой Origin, что остальные `/api/*`.
- Relay: `FrameType.Feed = 46` (клиент→агент, payload `{session, limit?, before?, after?}`)
  и `FrameType.FeedResult = 47` (агент→клиент, payload из §6).

**§10. Объявление возможностей.** `FrameType.Capabilities = 44` (клиент→агент,
`{caps: string[]}`) и `FrameType.CapabilitiesResult = 45` (агент→клиент, `{caps: string[]}`).
По LAN то же самое: `POST /api/capabilities` с телом `{caps}` → `{caps}`.

- Имя возможности этого этапа — `feed`. Список — данные, не тип: клиент хранит пересечение
  и спрашивает его по имени.
- Обмен один на подключение, до первого запроса ленты. Ответ агента не пришёл за 2 с — у
  агента возможностей нет; на LAN то же даёт ответ 404 на неизвестный маршрут.
- Незнакомый кадр агент уже игнорирует (`default: return`), клиент обязан делать так же.
- Пересечение видно в `/api/diag`: «надстройка промолчала» и «надстройка сломалась» иначе
  выглядят одинаково (ADR 0018).

**§11. Права гостя.** Кадр `Feed` попадает в разбор гостя рядом с `FilesList`: гостю со
`scope` разрешена только его сессия (проверка — та же, что в `doOpen`), чужая даёт
`forbidden`. Право `write` для ленты не требуется: пользователь решил «давать наравне»,
а лента ничего не меняет. Право `files` тоже не требуется: лента — не файловый доступ,
она не даёт прочитать произвольный путь.

**§12. Кэш и цена.** Ответ не кэшируется: файл дописывается, а чтение хвоста — это одно
позиционированное чтение 256 КиБ, дешевле любого кэша. Кэшируется (на 5 с, уже есть)
только ответ определителя «какой агент в панели».

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `transcript-feed` (агент) | приведением обоих форматов к `FeedEntry` и окном чтения по курсору | `readFeed(file, agent, opts) -> FeedPage \| FeedFailure`, `parseLine(line, agent) -> FeedEntry \| null` | разбор форматов, устройство курсора, границы строк, пределы |
| `feed-service` (агент) | связкой «имя сессии → панель → файл → страница ленты» и цепочкой Codex | `sessionFeed(name, opts) -> FeedResult` | вызов `resolve`, tmux, поиск файла-родителя |
| `capabilities` (протокол) | списком имён возможностей и их пересечением | `AGENT_CAPS`, `CLIENT_CAPS`, `intersect(a, b) -> string[]` | ничего — это данные |

**Шов для тестов один: `readFeed` над подложенными файлами.** Он чистый: на вход путь и
курсор, на выход страница. Живые агенты, tmux и сеть в нём не участвуют. Всё остальное
проверяется существующими швами проекта: `server.test.ts` для LAN-маршрута, моки транспорта
в вебе — для relay-кадров.

`sessionFeed` своего шва не заводит: он склейка над `resolve` (у того уже есть свой шов
`TranscriptSources`) и `readFeed`.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R11 — экран ленты в PWA | третий этап; здесь строится то, что он будет читать |
| Поиск по ленте | часть экрана, а не данных: ищет тот, кто показывает |
| Подписка на приращение (push) | клиент и так опрашивает сессии раз в 3 с; `after` по тому же опросу дешевле нового механизма подписки. Вернуться, когда экран покажет, что опрос заметен |
| Вывод инструментов | решение пользователя G01: «свёрнутые инструменты», без вывода |
| Лента по произвольному файлу | адресация только по сессии: иначе лента становится способом прочитать любой файл в обход прав |
| Хранение ленты на устройстве | на этом этапе лента нигде не оседает: агент читает файл и отдаёт страницу, клиент держит её в памяти экрана. Решение «историю на устройстве не шифруем» относится к локальной истории терминала (этап 3 дорожной карты) и здесь применять не к чему |
