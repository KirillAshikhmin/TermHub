# Спецификация: свой терминал, идеи mosh и удобство работы с агентами

Режим прогона: интервью · глубина: максимальная. Поставка этого прогона (решение
пользователя, вопрос 1) — **анализ, решения и дорожная карта**: документ с вердиктами,
ADR на каждое архитектурное решение и план этапов размером в PR. Код пишется
следующими прогонами по этим этапам.

---

## Задача

С телефона идёт настоящая работа: агенты (Claude Code, Codex) крутятся в tmux на Mac,
а человек отвечает им из метро, с дивана, из очереди. В этой работе мешает пять вещей.

Историю не пролистать. Пока агент печатал десять минут, ушло вверх всё интересное, и
достать его можно только пока есть связь: каждый шаг прокрутки — запрос в copy-mode
tmux по сети. В офлайне не листается ничего, даже то, что секунду назад было на экране.

Всё тормозит. Набранный символ едет до Mac и обратно. Прокрутка дёргается. Между тапом
по сессии и картинкой — пустой экран. После блокировки телефона или смены Wi-Fi на LTE
соединение поднимается заново и весь экран перерисовывается.

Полос ввода две. Claude рисует свою рамку внизу экрана, TermHub умеет показать свою
строку — и обе занимают место на маленьком экране. Сверху к этому добавляется статусная
строка tmux, которая на телефоне не нужна вовсе.

С агентами неудобно. На вопрос «1. Yes 2. No» приходится целиться стрелками. Когда сессий
несколько, непонятно, кто чего ждёт, — на дашборде только значок. Длинный промпт набирать
вслепую в терминал мучительно. Уведомление приходит без текста: непонятно, агент закончил,
спрашивает разрешения или упёрся в ошибку.

И общий вопрос, который всё это порождает: не пора ли взять терминал под свой контроль
вместо библиотечного, и не заменить ли tmux на mosh.

## Решение

**Библиотеку рендера не меняем — меняем модель подключения.** Ядро xterm.js остаётся
парсером и рендером (решение пользователя, вопрос 2). «Своим» становится всё, что вокруг:
как терминал соединяется с tmux, где живёт история, чем пользователь пишет, что видно на
экране, как ведут себя жесты и панели.

**tmux остаётся, mosh как замена отвергнут** (решение пользователя, вопрос 3). Из mosh
берутся три идеи поверх нынешнего WebSocket: возобновление с места разрыва вместо
перерисовки, предиктивное локальное эхо и роуминг сессии при смене сети.

Что получает пользователь, когда всё готово:

- История сессии листается пальцем мгновенно и без сети, потому что лежит на телефоне.
- Набранный символ появляется сразу, ещё до ответа Mac.
- Открытая сессия показывает картинку мгновенно, а после обрыва связи продолжает с места,
  а не перерисовывается заново.
- На экране одна полоса ввода, а не две, и нет статусной строки tmux.
- Ответить агенту «да» можно крупной кнопкой или прямо из уведомления, где виден текст вопроса.
- Дашборд показывает, кто чего ждёт, без захода в каждую сессию.
- Длинный промпт пишется в нормальном поле, диктуется голосом, к нему прикладывается картинка.

## Что измерено на живом tmux 3.7b (12.09.2026)

Вся спецификация опирается на эти замеры, а не на предположения. Проба гоняла tmux на
изолированном сокете через node-pty — ту же среду, в которой работает агент TermHub.

| Что проверено | Результат |
|---|---|
| Первые байты `tmux attach` | `ESC[?1049h` — клиент уходит в alt-screen сразу и до detach |
| Первые байты `tmux -CC attach` (control mode) | alt-screen не приходит **вообще**; поток строчный: `%begin/%end`, `%session-changed`, `%output %<pane> <байты в октальном экранировании>`, `%layout-change` |
| Статусная строка tmux в control mode | клиенту не приходит: UI рисует клиент |
| Стоимость подключения в control mode | **десятки байт** (83 в этой пробе, 78 в независимой — зависит от длины имени сессии), перерисовки экрана нет |
| Ввод произвольных байтов из control mode | `send-keys -t <сессия> -H <hex>` — работает, ошибок нет |
| Размер окна из control mode | `refresh-client -C 100x30` — работает, размер держится и после ухода клиента |
| История панели | `capture-pane -p -e -S -` отдаёт все строки до `history-limit`; проба шла на 4000 строках, сам лимит проект ставит в 50 000 |
| Цена истории | реалистичный цветной вывод — **89 байт на строку**, 3000 строк = 266 КБ, 57 мс на стороне tmux |
| Второй alt-screen — от приложения внутри панели | `vim` → `alternate_on=1`; **Claude Code 2.1.269 → `alternate_on=0`**, **Codex 0.153.4 → `alternate_on=0`** |
| Гарантия для Codex | у него есть флаг `--no-alt-screen` («preserving terminal scrollback history»); пресет TermHub уже передаёт Codex флаги через argv |

Отсюда четыре следствия, на которых стоит всё остальное:

1. **Причина «нет скролла офлайн» — не в xterm.js, а в alt-screen.** У альтернативного
   буфера истории нет по стандарту, поэтому ни один рендер её там не покажет.
2. **Control mode снимает эту причину целиком** и попутно убирает статусную строку tmux
   с экрана телефона, не трогая терминал IDE на том же сокете.
3. **Подключение в control mode почти бесплатно**, значит после обрыва можно продолжать,
   а не перерисовывать — если знать, что клиент уже видел.
4. **Агентские TUI alt-screen не занимают.** Это отдельный, второй alt-screen — его
   включает не tmux, а само приложение в панели; он и есть «полноэкранные приложения» из
   задачи. Замер показал, что Claude Code и Codex работают inline, а значит после снятия
   внешнего alt-screen их вывод копится в истории панели и становится листаемым. В
   alt-screen уходят vim и htop — там истории нет по природе, и это принимается.

**Расшифровка «вdt» из задачи.** Речь о веб-клиенте TermHub — PWA в `packages/web`,
где сейчас живёт терминал на xterm.js. Возражений на это чтение не поступило (вопрос 1).

## Depth pass

Проработка по восьми измерениям. Прогнана **по блокам**, а не по каждой строке
требования: 23 живых требования на восемь измерений дали бы 184 ячейки, из которых
большинство — «не применимо», и вердикты утонули бы в шуме. Каждый блок явно перечисляет
свои требования, так что покрытие сохраняется. Это осознанное отступление от правила
«каждое измерение для каждого требования».

### Блок 1. Модель подключения (R01, R02, R03, G02)

| Измерение | Решение |
|---|---|
| Первый запуск | Первое подключение к сессии: control mode даёт 83 байта и пустой экран, поэтому клиент сначала просит `capture-pane -p -e -S -N` и рисует срез, затем включает поток `%output` |
| Пусто | Сессия без вывода (только что создана) — экран пуст, приглашение шелла придёт первым же `%output`; заглушка не нужна |
| Неверный ввод | Битый `%output` (обрыв октальной последовательности на границе чанка) — накапливаем до конца строки, неполную не разэкранируем |
| Отказ | tmux старше 3.0, control mode не поднялся, `%error` в ответ — падаем обратно на нынешний `tmux attach` и пишем причину в лог; пользователь получает рабочий терминал, а не пустой экран |
| Прерывание | Клиент control mode убит на середине команды — `%begin` без `%end`: незавершённый блок отбрасывается целиком |
| Рост | Панелей и окон в сессии больше одной: слушаем `%layout-change`, показываем активную панель; разделение экрана — вне рамок этого прогона |
| Второй alt-screen | Приложение в панели ушло в alt-screen (vim, htop): истории у него нет по природе, показываем пометку; по выходе история снова листается. Для Codex профиль добавляет `--no-alt-screen` |
| Границы | Read-only гость: ввод не шлём, `send-keys` не вызываем — запрет уже на агенте, повторяем на клиенте |
| Последствия | `refresh-client -C` меняет размер окна всем клиентам сессии — так же, как сегодня; пользователь это подтвердил (вопрос 8) |

### Блок 2. История на устройстве (R04, R16i)

| Измерение | Решение |
|---|---|
| Первый запуск | Истории нет — тянем срез с Mac, показываем его и с этого момента копим сами |
| Пусто | Нет связи и нет сохранённого: честный экран «истории пока нет», а не вечный спиннер |
| Неверный ввод | Хранилище недоступно (приватный режим, переполнение квоты) — работаем в памяти, функция деградирует молча, ошибку в лог |
| Отказ | Запись не удалась — терминал продолжает работать; история просто не переживёт перезапуск |
| Прерывание | Приложение убито на середине записи — читаем то, что записалось; хвост без завершающей записи отбрасываем |
| Рост | 89 байт на строку ⇒ 50 000 строк ≈ 4.4 МБ на сессию. Лимит: 10 000 строк на сессию (≈ 900 КБ), вытеснение старых. iOS чистит хранилище после 7 дней без запуска — это принято, восстановление идёт с Mac |
| Границы | Гость по одноразовому коду не пишет ничего. Отзыв устройства и выход чистят всё сохранённое |
| Последствия | История — вывод терминала со всем, что там было; шифрование персиста пользователь отклонил как непропорциональное (вопрос 4) |

### Блок 3. Отзывчивость (R06, R14i)

| Измерение | Решение |
|---|---|
| Первый запуск | Задержка ещё не измерена — эхо выключено, включается после первых замеров |
| Пусто | Нечего эхоить (нет ввода) — поведение не отличается от нынешнего |
| Неверный ввод | Эхо не угадало (автодополнение, подсветка синтаксиса, перерисовка TUI) — приходящий `%output` побеждает, локальное предположение стирается |
| Отказ | Связь пропала на середине ввода — набранное остаётся в очереди, помечено «не подтверждено», уходит после восстановления |
| Прерывание | Реконнект: клиент сообщает номер последнего принятого куска вывода, агент досылает пропущенное из кольцевого буфера; буфер не покрывает разрыв — тянем `capture-pane` и перерисовываем один раз |
| Рост | Быстрый вывод (`yes`, сборка) — кольцевой буфер на агенте ограничен по байтам, при переполнении честно говорим «продолжение с перерисовкой» |
| Границы | Эхо только для сессий, где ввод разрешён; read-only гость эхо не получает |
| Последствия | Эхо рисует то, чего Mac ещё не видел — при отказе отправки оно должно исчезнуть, иначе пользователь поверит в отправленное |

### Блок 4. Полосы и место на экране (R07, G01, G02)

| Измерение | Решение |
|---|---|
| Первый запуск | Своя строка ввода закрыта — рамка агента видна, всё как сегодня |
| Пусто | В сессии обычный шелл без рамки — скрывать нечего, логика молчит |
| Неверный ввод | Рамка не распознана (другой агент, своя тема, перерисовка на середине) — ничего не скрываем: сомнение решается в пользу «показать» |
| Отказ | Детектор ошибся и срезал полезное — возврат мгновенный, по закрытию своей строки |
| Прерывание | Своя строка открыта, агент сменил режим (план, выбор из списка) — скрытие снимается, пока идёт выбор |
| Рост | Рамка выросла (многострочный черновик в Claude) — скрываем по фактической высоте, а не по числу строк |
| Границы | Скрытие живёт только на клиенте: IDE на том же сокете видит всё |
| Последствия | Скрытое — часть картинки, а не удалённые данные; копирование и поиск видят полный экран |

### Блок 5. Работа с агентами (R11, G06, G08–G11, R15i)

| Измерение | Решение |
|---|---|
| Первый запуск | Уведомления ещё не разрешены — кнопка «разрешить» остаётся как сегодня |
| Пусто | Агент ничего не спрашивал — кнопок ответа нет, карточка показывает последние строки |
| Неверный ввод | Вопрос распознан неверно — кнопки не показываем, обычный ввод работает; никогда не шлём байты «на всякий случай» |
| Отказ | Ответ из уведомления не дошёл (Mac спит, сессия убита) — уведомление говорит об этом, а не молчит |
| Неизвестный агент | Профиля нет: терминал, история, скролл, эхо и жесты работают полностью; молчат только скрытие рамки, кнопки ответа и текст в уведомлении |
| Прерывание | На вопрос ответили и с телефона, и в IDE — выигрывает первый; второй получает отказ, а не дубль |
| Рост | Десять сессий с агентами — дашборд показывает ждущих первыми; уведомления троттлятся как сегодня |
| Границы | Ответ из уведомления требует права записи; гостю read-only кнопок нет |
| Последствия | Текст вопроса уходит в push — payload шифруется до браузера, Apple и Google его не видят; на локскрине виден, это принято (вопрос 12) |

### Блок 6. Жесты и навигация (G04, G05, G07)

| Измерение | Решение |

| Первый запуск | Жесты работают сразу, обучающих подсказок нет |

| Неверный ввод | Пинч перепутан со скроллом — порог по числу пальцев и дистанции; один палец всегда скролл |
| Отказ | Границы блоков не размечены (шелл без меток, чужой агент) — навигация по блокам недоступна, скролл работает |
| Прерывание | Свайп прерван на середине — возврат к текущей сессии, терминал не пересоздаётся |
| Рост | Много сессий — свайп идёт по порядку вкладок, край списка не зацикливается |
| Границы | Свайп не конфликтует с выделением текста: при активном выделении жест отдаётся выделению |
| Последствия | Пинч меняет размер окна tmux для всех клиентов сессии — то же поведение, что у кнопок A−/A+ сегодня |

## Решения по реализации

Каждое решение — с одной строкой «почему так». Пути к файлам не пишем: они устареют
раньше спецификации.

### §1. Своё окно терминала = своя обвязка, ядро xterm.js остаётся

Ядро xterm.js продолжает разбирать поток и рисовать. TermHub владеет всем остальным:
подключением, историей, вводом, панелями, жестами, оверлеями.

**Почему так.** Боли задачи не в рендере. Скролл офлайн упирается в alt-screen,
отзывчивость — в сетевой круг до Mac, полосы ввода — в раскладку экрана. Свой VT-парсер
не двигает ни одну из них, зато открывает месяцы работы на паритет: ширины Unicode,
mouse-протоколы SGR и X10, DEC-режимы, OSC 7/8/52, bracketed paste, композиция IME на
мобильных клавиатурах. Отвергнуты два варианта: свой рендер над `@xterm/headless`
(отдаёт аддоны WebGL, поиска и ссылок, а выигрыш нужен только при нестандартном виде
экрана — держим в резерве) и свой эмулятор с нуля (максимальная цена при минимальной
отдаче на этих задачах).

### §2. Control mode вместо `tmux attach`

Терминал подключается через `tmux -CC attach`. Клиент разбирает строчный протокол
`%output/%begin/%end/%layout-change`, разэкранирует октальные последовательности и
отдаёт байты в xterm. Ввод — `send-keys -H`, размер — `refresh-client -C`, начальный
экран и восстановление — `capture-pane -p -e -S -N`.

**Почему так.** Это единственное изменение, которое закрывает сразу четыре требования:
терминал перестаёт быть в alt-screen (значит появляется настоящий локальный scrollback —
R03, R04), статусная строка tmux перестаёт приходить клиенту (G02), подключение дешевеет
до 83 байт (основа для R06.4), а UI сессий переходит под контроль TermHub (R02).
Проверено на живом tmux 3.7b. Так же устроена интеграция iTerm2 с tmux — путь известный.

**Второй alt-screen — отдельная работа того же этапа.** Control mode снимает alt-screen,
который шлёт `tmux attach`. Alt-screen, который включает само приложение в панели, остаётся
за приложением: замер показал, что Claude Code и Codex его не включают, а vim и htop
включают. Для Codex гарантия закрепляется флагом `--no-alt-screen` в пресете запуска — он
у него есть и означает ровно «inline, сохраняя scrollback». Приложение, ушедшее в
alt-screen, помечается в интерфейсе, чтобы отсутствие истории читалось как свойство
приложения, а не как поломка TermHub.

**Цена.** Каждый ввод становится командой tmux с ответом `%begin/%end`; разэкранирование
на горячем пути; протокол control mode чувствителен к версии tmux. Поэтому §3.

### §3. Откат на нынешний режим — обязателен, но это не fallback-архитектура

Если control mode не поднялся или ответил `%error`, терминал работает через нынешний
`tmux attach`. Одно место принятия решения, при подключении, с записью причины в лог.

**Почему так.** Пользователь может обновить tmux до версии, где протокол другой, и
остаться без терминала вообще. Это не дублирующая ветка «на всякий случай»: обе дороги
уже существуют в коде, выбор делается один раз и виден в диагностике.

### §4. История живёт на клиенте, с лимитом и без шифрования

Вывод копится в буфере xterm (обычный буфер, а не alt) и пишется в хранилище браузера
порциями. Лимит 10 000 строк на сессию, вытеснение старых. Гость по одноразовому коду
не пишет. Выход и отзыв устройства чистят.

**Почему так.** 89 байт на строку — замерено; 10 000 строк ≈ 900 КБ на сессию, десять
сессий ≈ 9 МБ, что помещается в квоты мобильных браузеров. Шифрование персиста
пользователь отклонил (вопрос 4): оно защищает от чтения базы другим приложением на
взломанном телефоне и не защищает от разблокированного телефона в чужих руках.

### §5. Из mosh берём три идеи, сам mosh не берём

- **Возобновление вместо перерисовки.** Агент нумерует куски вывода и держит кольцевой
  буфер; клиент при подключении говорит номер последнего принятого, агент досылает
  пропущенное. Не покрывает — один `capture-pane` и перерисовка.
- **Предиктивное эхо.** Клиент рисует набранное сразу, помечая неподтверждённое; приходящий
  вывод от Mac всегда побеждает. Включается по измеренной задержке.

  Предсказываются только **печатные символы и забой** в текущей строке: вставка символа в
  позицию курсора и удаление предыдущего. Не предсказываются никогда: управляющие
  последовательности, Enter, Tab, стрелки, любые сочетания с Ctrl, Alt и Cmd, вставка из
  буфера. Эхо выключено целиком, пока терминал в одном из состояний: приложение просит
  скрыть ввод (пароль), включён mouse tracking, экран в alt-screen, идёт bracketed paste,
  сессия read-only. Неподтверждённые символы рисуются приглушённо и исчезают, как только
  приходит вывод от Mac, перекрывающий их позицию, либо по таймауту 1 с без подтверждения.
  Курсор при этом рисуется в предсказанной позиции, а на подтверждении встаёт туда, куда
  его поставил Mac.

  **Почему такой узкий набор.** Предсказать можно только то, что гарантированно означает
  одно и то же в любом приложении. Символ в строке ввода означает символ везде; Tab
  означает автодополнение в шелле, отступ в редакторе и переход по кнопкам в TUI.
- **Роуминг.** Сессия на агенте переживает смену сети: реконнект продолжает ту же сессию
  по её идентификатору, а не начинает новую.

**Почему так.** mosh как транспорт несовместим с продуктом по трём причинам сразу:
слушает входящий UDP (обещание «на Mac не открывается ни один порт» ломается), не имеет
scrollback (убивает главное требование задачи), не поддерживает несколько клиентов на
сессию и не имеет браузерного клиента. Ценность mosh — в идеях его протокола, а идеи
переносимы на нынешний WebSocket.

### §6. Скрытие рамки ввода агента — визуальное, обратимое, с презумпцией «показать»

**Чем управляется.** Тем же тумблером ✎, который сегодня открывает и закрывает свою
строку ввода в панели быстрых клавиш. Нового переключателя не появляется: пользователь
выбрал связку «открыта своя строка → рамка скрыта» (вопрос 7).

**Как находится рамка.** Снизу вверх по строкам экрана, по трём признакам подряд:

1. Нижняя граница — строка, состоящая только из символов рисования рамки и пробелов
   (`─ ━ ═ ╰ ╯ ╚ ╝ └ ┘` и их соседи по блоку Box Drawing).
2. Боковые границы — строки, начинающиеся и заканчивающиеся вертикальным символом
   рисования (`│ ┃ ║ | ▏`), идущие непрерывно вверх от нижней границы.
3. Верхняя граница — строка из символов рисования с углами (`╭ ┌ ╔ ┏`).

Регион — от верхней границы до низа экрана; высота считается по факту каждый раз, а не
запоминается. Поиск идёт не дальше половины высоты экрана вверх: рамка ввода занимает низ,
а половина экрана — это уже не рамка. Ниже рамки допускаются строки подсказок без рамки
(«esc to interrupt», счётчик контекста) — они входят в регион.

**Когда не скрываем — все случаи:** признаки не сошлись; регион выше половины экрана; в
регионе распознан вопрос с вариантами (§7); приложение в alt-screen; агент неизвестен
(§10a); экран уже 10 строк или ниже. Сомнение всегда решается в пользу «показать».

**Почему так.** Рамка — часть картинки TUI, её нельзя «выключить» на стороне агента.
Ошибка детектора в сторону «скрыл лишнее» стоит дороже, чем в сторону «показал лишнее»:
пользователь не увидит вопроса и решит, что агент завис. Отвергнут вариант держать
фиксированную высоту рамки: в Claude Code она растёт вместе с черновиком.

### §7. Ответ на вопрос агента кнопками

**Что считается вопросом.** Блок в нижней части экрана, где идут подряд строки вида
«номер, разделитель, текст» (`1. Yes`, `2) No`, `❯ 1. Да`) — не меньше двух, не больше
девяти, номера подряд с единицы. Признак выбора курсором (`❯`, `>`, инверсия) не
обязателен, но если есть — подсвечиваем текущий вариант.

**Что шлёт кнопка.** Ровно то, что набрал бы человек: цифру варианта и `Enter`. Для
вопросов «да/нет» без номеров (`(y/n)`) — соответствующую букву без `Enter`, как ждёт
агент. Соответствие «вариант → байты» задаётся профилем агента (§10a), а не угадывается.

**Когда кнопок нет:** вариантов меньше двух или больше девяти; номера не подряд; агент
неизвестен; сессия read-only; вопрос ушёл с экрана (перерисовка) — кнопки гаснут вместе
с ним.

**Почему так.** Это самая частая операция на телефоне и самая неудобная сейчас. Правило
«не распознали — молчим» обязательно: отправка байтов по догадке в сессию с агентом,
который умеет менять файлы, недопустима.

### §8. Уведомления с текстом и ответом из уведомления

В уведомление кладётся текст вопроса или итога и кнопки ответа. Payload web-push
шифруется до браузера, посредники видят только шифротекст.

**Почему так.** Пользователь выбрал видимый текст (вопрос 12): решать, идти ли к телефону,
надо не открывая его. Сокрытие на локскрине — штатная настройка iOS и Android.

### §9. Строка ввода становится настоящим редактором

Многострочное поле с курсором, выделением и правкой середины; черновик переживает
сворачивание и переключение сессий; кнопка диктовки; вложение картинки через временную
папку на Mac.

**Почему так.** Пользователь отметил боль «длинный промпт», но отказался от заготовок
промптов и вставки путей (вопросы 10, 11) — значит лечить надо сам процесс набора, а не
обкладывать его шаблонами.

### §10a. Профили агентов — «и другими» из задачи

Всё, что TermHub знает про конкретного агента, лежит **в профиле-данных**, а не в коде:
имя процесса и заголовок, по которым агент опознаётся; символы рамки ввода; форма вопроса
с вариантами; байты ответа на вариант; что означает «занят» и «ждёт ответа»; аргументы
запуска для пресета. Встроенных профилей два — Claude Code и Codex; добавление третьего
(Gemini CLI, aider, opencode) — новая запись, а не правка логики.

**Неизвестный агент получает базовое поведение, а не поломку:** терминал, история,
скролл, эхо, панели и жесты работают полностью; молчат только надстройки, которым нужен
профиль — скрытие рамки, кнопки ответа, текст в уведомлении. Это же поведение —
страховка при обновлении агента, сменившего вид экрана.

**Почему так.** Задача называет «claude, codex и других». Агенты меняют TUI чаще, чем
выходят релизы TermHub, и эвристика, зашитая в код, ломается молча и целиком. Профиль
как данные позволяет починить распознавание одной записью и деградировать до честного
«ничего не знаю про этот агент» вместо ложных кнопок.

### §10. Совместимость протокола

Кадры между агентом и вебом расширяются, старые не ломаются: клиент объявляет
поддерживаемые возможности при подключении, агент отвечает тем, что умеет.

**Почему так.** Агент на Mac и PWA в браузере обновляются в разное время; кэш service
worker может держать старую версию неделями. Без объявления возможностей пользователь
получит чёрный экран после обновления агента.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `control-protocol` | разбором строк control mode | `parse(chunk) -> Event[]` (`output` / `layout` / `reply` / `error`), `escapeInput(bytes) -> string` | октальное экранирование, склейку чанков, состояние `%begin/%end` |
| `session-link` (агент) | жизненным циклом control-клиента, нумерацией вывода, кольцевым буфером | `open(session, opts) -> Link`, `Link.resumeFrom(seq)`, `Link.write(bytes)`, `Link.resize(cols, rows)`, `Link.snapshot(lines)` | выбор control mode или attach, откат, спавн pty |
| `term-history` (веб) | локальной историей сессии и её персистом | `append(session, bytes)`, `read(session) -> bytes`, `clear(session)`, `size(session) -> bytes` | хранилище, лимит, вытеснение, деградацию без хранилища |
| `echo` (веб) | предиктивным локальным эхо | `predict(bytes)`, `confirm(seq)`, `reset()`, `enabled(rtt) -> boolean` | порог задержки, разметку неподтверждённого |
| `agent-ui` (веб) | распознаванием рамки ввода, вопроса и границ блоков | `frame(screen) -> Region \| null`, `question(screen) -> Choice[] \| null`, `blocks(buffer) -> Bound[]` | эвристики под Claude Code и Codex |
| `agent-profiles` | знанием о конкретных агентах как данными | `profiles: Profile[]`, `match(session) -> Profile \| null` | состав профиля, порядок сопоставления |
| `prompt-editor` (веб) | строкой ввода, черновиком, диктовкой, вложениями | `mount(host, handlers) -> Editor`, `Editor.draft()`, `Editor.send()` | хранение черновика, работу с файлами |

**Швы для тестов — два, и оба уже есть по смыслу в проекте:**

1. `control-protocol.parse` — чистая функция над байтами. Весь разбор протокола проверяется
   здесь, без tmux и без DOM.
2. `agent-ui` — чистые функции над снимком экрана и профилем. Все эвристики распознавания
   проверяются на зафиксированных снимках вывода Claude Code и Codex, плюс снимок
   неизвестного агента, на котором надстройки обязаны промолчать.

Всё остальное проверяется через существующие швы проекта: моки транспорта в вебе и
изолированный tmux-сокет в тестах агента.
