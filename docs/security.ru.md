# Безопасность

[English](security.md) · **Русский**

Кратко о том, что и как защищено, и на какие компромиссы TermHub идёт
осознанно.

## Локальная сеть (LAN)

- По умолчанию — обычный HTTP, не HTTPS, и агент слушает на всех сетевых
  интерфейсах (`0.0.0.0`). Это осознанный компромисс ради простоты:
  настройка не требует сертификатов, а трафик не покидает Wi-Fi-сеть.
  Доступ защищён паролем: в конфиге хранится не сам пароль, а его
  scrypt-хеш, сравнение идёт в постоянном времени (устойчиво к атакам по
  времени ответа).
- **Граница доверия — ваша локальная сеть.** Раз трафик идёт по HTTP,
  пассивный слушатель в том же сегменте (например, на общем или публичном
  Wi-Fi) способен перехватить пароль при входе и 30-дневную auth-cookie.
  Поэтому режим «HTTP + пароль» рассчитан на домашнюю/доверенную сеть.
  Для доступа из недоверенной сети используйте relay (весь трафик
  end-to-end-шифрован, см. ниже), Tailscale или включите TLS. `termhub
  setup` явно предупреждает об этом, когда TLS не настроен.
- Успешный вход выдаёт HttpOnly-cookie (подписана HMAC, секрет для подписи
  генерируется при `termhub setup`), действует 30 суток; WS-подключение к
  терминалу проверяет ту же cookie.
- На `/api/login` — rate-limit: не больше 5 неудачных попыток в минуту с
  одного IP.
- Если нужен HTTPS даже в LAN — доступна опция TLS (mkcert или
  `tailscale cert`, см. [docs/notifications.ru.md](notifications.ru.md) и
  [docs/remote.ru.md](remote.ru.md)): пути к файлам сертификата/ключа
  добавляются в `~/.termhub/config.json` вручную, `setup` их не создаёт.

## Удалённый доступ (relay)

**Что видит relay.** Метаданные подключения: `agentId` (отпечаток
долговременного открытого ключа агента), публичный ключ подключающегося
клиента (он нужен для маршрутизации и обмена ключами — это адрес, а не
секрет), тайминги и объём трафика. Само содержимое (нажатия клавиш, вывод
терминала) идёт внутри end-to-end-шифрованного потока, ключей от которого у
relay попросту нет. Имя устройства клиента relay не видит — оно передаётся
агенту только внутри зашифрованного канала пейринга.

**Криптосхема (libsodium):**

- У агента и у каждого клиента — собственная долговременная пара ключей
  Ed25519 (identity).
- **Пейринг нового устройства** — по одноразовому коду
  (`XXXX-YYYY-YYYY-YYYY`: 12 символов из 30-значного алфавита без похожих
  друг на друга букв/цифр, это около 59 бит энтропии). Из кода обе стороны
  выводят общий ключ `K_pair`; relay сам секрета не знает и подобрать его не
  может — комната пейринга живёт всего 5 минут и допускает не больше
  3 попыток. Внутри канала, зашифрованного `K_pair`, стороны обмениваются
  публичными ключами и подтверждают личность подписью.
- **Обычная сессия:** X25519-обмен ключами (`crypto_kx`) → пара сессионных
  ключей → весь трафик в обе стороны идёт через
  `crypto_secretstream_xchacha20poly1305`.
- **Доверие — по принципу TOFU** (trust on first use): один раз успешно
  спарившись, устройство остаётся доверенным, пока его явно не отозвали.
  Никакого центра сертификации — только ключи и факт пейринга.
- **Отзыв устройства:** `termhub devices` / `termhub revoke <fingerprint|имя>`
  на Mac. После отзыва устройство не проходит новый E2E-хендшейк и не может
  открывать новые терминалы даже по уже установленному соединению. Уже
  открытые в этот момент терминалы продолжают жить до разрыва соединения —
  чтобы оборвать их немедленно, перезапустите агента (`termhub start`).

**Про forward secrecy.** Сессионные ключи выводятся из долговременных
ключей устройств (статический Диффи–Хеллман), эфемерных ключей на сессию
нет. Практический смысл: если чей-то долговременный приватный ключ будет
скомпрометирован, злоумышленник, заранее записавший зашифрованный трафик
(например, на самом relay), сможет его расшифровать задним числом. Это
осознанный компромисс: relay по построению трафик не хранит, а живой канал
остаётся конфиденциальным и защищённым от подмены. Если ваша модель угроз
требует perfect forward secrecy, это направление для будущей версии
(эфемерный X25519 поверх аутентификации по identity).

## Защита от произвольных команд (anti-RCE)

API агента не исполняет что попало:

- каталог для новой сессии — только из заранее заданного списка
  (`sessionRoots` в конфиге, по умолчанию `~/projects`), никакого
  произвольного пути;
- команда для новой сессии — только один из пресетов (`zsh` или `claude`),
  не свободный ввод;
- все обращения к `tmux` идут через `execFile` без участия shell —
  исключена инъекция через спецсимволы в имени сессии или каталоге.

## Секреты на диске

`~/.termhub/` (конфиг, identity-ключи, список авторизованных устройств,
push-подписки) создаётся с правами `0700`, отдельные файлы — `0600`.
Приватный ключ VAPID (для Web Push) и долговременный приватный ключ агента
никогда не покидают Mac — по сети передаются только их публичные части.
