# CLAUDE.md

Инструкции для работы с кодом **TermHub**. Прочитай перед любыми правками.
Общение — на русском.

## Что это

TermHub даёт доступ к терминальным (tmux) сессиям Mac с телефона/браузера.
Два режима: **LAN** (PWA + пароль, прямое WS-подключение к агенту) и **remote**
(тонкий zero-knowledge relay + E2E-крипта, пейринг по одноразовому коду) плюс
CLI-клиент «ssh через relay».

Полный обзор — `README.md`; безопасность — `docs/security.md`; удалённый доступ —
`docs/remote.md`. Статус — `0.1.0` alpha.

## Монорепо (npm workspaces, `packages/*`)

| Пакет            | Что внутри |
|------------------|------------|
| `@termhub/protocol` | Фундамент: фрейм-кодек (`frames.ts`), E2E-крипта на libsodium (`crypto.ts`), base64 (`b64.ts`). Зависимость всех остальных. |
| `@termhub/agent` | Node-процесс на хосте (macOS/Linux) + CLI `termhub`. HTTP/WS-сервер (`server.ts`+`auth.ts`), обёртка tmux (`sessions.ts`), мост pty↔tmux↔WS (`bridge.ts`), web-push (`push.ts`), автозапуск LaunchAgent/systemd (`service.ts`), конфиг/setup (`config.ts`/`setup.ts`/`paths.ts`), remote-сторона (`relay-link.ts`/`share.ts`), CLI-клиент (`connect-cmd.ts`/`pair-cmd.ts`/`client-store.ts`/`devices-cmd.ts`), роутер команд (`cli.ts`). |
| `@termhub/relay` | Zero-knowledge коммутатор (VPS, Docker): `index.ts`+`rooms.ts`, раздача статики `static.ts`, точка входа `main.ts`. |
| `@termhub/web`   | PWA (vite + vanilla TS, xterm.js). Транспорт-абстракция `transport.ts`/`relay-transport.ts`, экраны `dashboard.ts`/`term.ts`/`pairing.ts`, SW `sw.ts`, крипта-в-браузере `keys.ts`/`remote.ts`. Собирается в `packages/agent/static` (раздаётся агентом). |

Технологии: Node ≥ 22, TypeScript strict (ESM везде), `ws`, `node-pty`,
`libsodium-wrappers-sumo`, `web-push`, vite, `@xterm/*`, vitest.


## Критические знания (иначе не вывести из кода)

1. **tmux — обязательный фундамент.** К обычной сессии терминала IDE снаружи
   не подключиться (pty принадлежит IDE). Рабочие сессии запускаются внутри
   tmux (`setup` заводит алиас `tm`), агент делает `tmux attach`. Без tmux
   продукт не работает.

2. **`packages/{agent,relay}/static` — сборочный артефакт (в `.gitignore`).**
   Тесты гоняются по `src` без сборки. Порядок `npm run build && npx vitest run`
   раньше ломал тест-заглушку — теперь тест изолирован (передаёт пустой
   `staticDir`), но **держи дерево чистым перед прогоном**: если сомневаешься,
   `rm -rf packages/{agent,relay}/static` перед `npx vitest run`.

3. **Крипто-роли фиксированы:** агент = `server`, клиенты (web/CLI) = `client`
   в `sessionKeys`. Хендшейк: plaintext `hello{edPub}` → проверка fingerprint ∈
   authorized → `hello-ok{header, nonce}` → `hello-fin{header, sig}` → secretstream.
   `sig` — подпись транскрипта (`handshakeTranscript` в protocol/crypto.ts) свежего
   челленджа обоими header'ами: без неё агент в streaming НЕ пускает, и это
   единственное, что защищает от переигрывания записанной сессии недоверенным relay.
   Роли и подпись web/CLI/agent должны оставаться зеркальными — при правке хендшейка
   меняй все три стороны согласованно и гоняй `e2e.full.test.ts`.

4. **tmux в тестах — только изолированный сокет** `-L termhub-test-<uniq>` +
   `kill-server` в teardown. Никогда не трогай дефолтный tmux-сервер. Все вызовы
   tmux — через `execFile` без shell (анти-RCE); имена/каталоги валидируются
   (`^[\w.-]{1,40}$`, whitelist корней, пресеты команд).

4a. **В проде рабочие сессии живут на выделенном сокете** `-L termhub`
   (`config.TMUX_SOCKET`) — чтобы случайный `tmux kill-server` (без `-L`) не
   сносил рабочие сессии. Имя сокета — единый источник: `cli.ts` прокидывает
   `TMUX_SOCKET` в `SessionService`/`wireTerminalWs`/`RelayLink`, а `setup`
   печёт его в `tm`/`tml` (`-L termhub …`). Меняешь имя — согласуй обе стороны.

5. **Если pty/tmux не спавнится в песочнице** (posix_spawn/EPERM) — перезапусти
   команду тестов с `dangerouslyDisableSandbox: true` (для локального дев-окружения).

6. **libsodium не должен попадать в LAN-бандл.** Крипта грузится ленивым
   `import('./remote')` только в relay-режиме. Проверка: в собранном
   `packages/agent/static/assets/main-*.js` не должно быть `libsodium`/`crypto_kx`
   (грепом). Фрейм-кодек тяни из `@termhub/protocol/frames` (без крипты).

  (русский); при правке держи обе версии синхронными. Доки в `docs/` — на русском.

  проекте не заводим — работа сливается прямо в неё. Remote — GitHub (`origin`), но пуш
  только по явной просьбе.

## Прежде чем сказать «готово»

`npx vitest run` зелёный на чистом дереве, при правке remote — прогнать
`packages/agent/test/e2e.full.test.ts` (живой E2E агент↔relay↔клиент).

**Деплой обязателен при любом изменении.** Цикл: изменил → проверил (тесты/сборка)
→ **задеплоил relay**. Процедура (см. [[relay-vps-deploy]]): `npm run build` →
`rsync … root@203.0.113.10:/root/termhub-src/` → на сервере
`docker build -t termhub-relay:latest -f packages/relay/Dockerfile .` →
`docker compose up -d` → проверить `curl --resolve relay.example.com:9443:203.0.113.10`.
Правка агента (`packages/agent/src`) — ещё и рестарт локального LaunchAgent
(`launchctl kickstart -k gui/$(id -u)/dev.termhub.agent`); web-only — только пересборка
(агент раздаёт static с диска). **web НЕ типизируется сборкой** (`vite build` без tsc) —
после правок web гоняй `npx tsc -p packages/web/tsconfig.json --noEmit`, иначе висячие
ссылки (типа удалённой переменной) проскочат в рантайм.

Примечание: `packages/web/src/relay-transport.ts` даёт предсуществующую tsc-придирку
(Uint8Array/BlobPart) — не блокер, рантайму безразлично.

## Терминал: control mode

К сессии подключаемся через `tmux -CC attach` (control mode) с обязательным откатом на прежний `tmux attach` — этап 1 дорожной карты, решение ADR 0014.

- `packages/agent/src/control-protocol.ts` — чистый разбор строчного протокола (`ControlParser.parse`, экземпляр один на соединение: держит хвост строки и открытый блок) и кодирование ввода для `send-keys -H` (`escapeInput`); ни процессов, ни сети — на этом шве протокол проверяется без живого tmux.
- `packages/agent/src/session-link.ts` — жизненный цикл control-клиента: выбор режима, активная панель, очередь команд и ввода, снимок `capture-pane` и откат; единственное место, где поднимается и гасится pty-клиент tmux, и один слот `PtyPool` на Link (откат второй слот не тратит).
- `packages/agent/src/pty-common.ts` — границы размера терминала (20–500 × 5–300) одним экземпляром на все мосты; `bridge.ts` и `relay-link.ts` своих копий не держат и pty не спавнят, `bridge.ts` остался обвязкой WS поверх `TerminalHandle`.
- `packages/web/src/term-mode.ts` — просьба клиента (`termhub.terminalMode`) и последний названный агентом режим (`termhub.terminalModeLast`). Выбирают просьбу в окне настроек (раздел «Подключение»), там же названо, каким способом агент подключил на самом деле; чипа режима в шапке терминала больше нет. Страница диагностики берёт режим оттуда же — в `/api/diag` агент его не отдаёт.
- Порядок решения: `terminalMode` в конфиге агента (`readTerminalMode`, по умолчанию `control`, значение `attach` запрещает control на всей машине) старше просьбы клиента, обе — старше живой проверки; не поднялся control — откат на `tmux attach` с причиной в логе.
- Просьба едет первым кадром открытия: в LAN это поле `mode` в первом RESIZE, через relay — `mode` в OPEN (терминал relay создаётся на OPEN, к RESIZE решение уже принято). Снимается один раз на открытие: реконнект живого канала повторяет тот же снимок, новая просьба ждёт нового открытия.
- `FrameType.TerminalState = 43`, payload `{mode?, altScreen?, cols?, rows?}` — от агента клиенту на каждое изменение; поля независимы и отбрасываются поштучно (`cols`/`rows` — только парой), а клиент, который кадра не знает, обязан его пропустить (ADR 0018).
- Снимок несёт состояние панели (ADR 0035): следом за `capture-pane` идёт запрос `TH-STATE` (`stateQuery`/`parsePaneState`), `renderSnapshot` дописывает курсор (на обычном экране — относительно конца снимка, в альтернативном — абсолютно, после `?1049h`) и режимы приложения. Вывод глушит только сам снимок, запрос состояния — нет.
- Размер панели в control mode — не размер клиента: `refresh-client -C` лишь просьба, а среди control-клиентов tmux слушает только подключившегося последним (ввод через `send-keys` активностью клиента не считается). Поэтому `resize()` в `session-link.ts` сначала шлёт `switch-client -t =<сессия>:` (делает клиента «последним», `window-size` не трогает) — размер задаёт тот, с кем работают. Агент называет размер панели (`onPaneSize`, при подключении и на `%layout-change`), веб держит экран этого размера (`paneSize` против `wanted` в `term.ts`); пока размер чужой, экран вписан масштабом (`fitForeign`), а ввод или касание шлют просьбу заново (`claimSize`, не чаще раза в секунду). Сама смена размера панели просьбу не повторяет — иначе клиенты перетягивают окно.
- Смена размера панели пересобирает экран клиента (`resync` → `renderScreen`): стирание и видимый экран панели с абсолютными позициями, живой вывод на это время придержан (`held`). Первая — нет: она часть подключения. Без этого приложение после смены размера дорисовывает себя не в те строки.
- Веб досылает размер через 350 мс после смены видимой области (`resendSoon`): одна потерянная просьба иначе оставляла агенту прежний размер.
- Через relay снимок ждёт первого `resize()` (`awaitFirstResize`, до 700 мс): терминал там создаётся на OPEN с размером по умолчанию.
- Заявка размера (`claim`): в control mode окно сессии держит один клиент tmux, и `switch-client` на свою сессию делает им нас. Заявлять вправе только экран, на котором работают: кадр RESIZE несёт `claim` (`resizePayload` в `ws-frames.ts`, оба провода), веб ставит его по действию человека за последние 10 с (`activeHere` в `term.ts`: ввод, касание, открытие терминала при фокусе страницы), пассивная вкладка шлёт `claim: false`. Поля нет (старый клиент) — заявка есть. Агент (`Link.resize(cols, rows, claim)`) шлёт `switch-client`, только если просьба новая или после прошлой заявки размер панели менялся; ту же просьбу `refresh-client -C` дважды не шлёт (`askSize`).
- Сравнивать просьбу с известным размером панели («уже наш — заявка не нужна») НЕЛЬЗЯ: размер панели приходит ответом на запрос и в момент заявки бывает устаревшим — заявка пропадала молча (поймано живым тестом `session-link.tmux.test.ts`). По той же причине после своей заявки экран пересобирается всегда (`resyncAfterClaim`), даже если размер «не менялся».
- Пересборка экрана (`resync`/`renderScreen`) и снимок (`renderSnapshot`) называют буфер (`?1049h`/`?1049l`) и каждый известный режим приложения явно (`modes`): вывод, пришедший на время захвата, клиенту не идёт, и переключения режимов в нём терялись бы, а экран клиента не обязан быть свежим — он переживает переподключение и помнит мышь и альтернативный экран приложения, которое уже вышло. Захват с состоянием — один `capture()` на снимок и пересборку. Переполнение придержанного вывода (1 МиБ) помечает картинку устаревшей (`resyncStale`): на экран она уже не идёт. Смена активной панели тоже пересобирает экран.
- Переподключение (`resume`): экран клиента уже жил, и снимок с историей лёг бы под показанный текст вторым экземпляром. Клиент помечает первое сообщение подключения (LAN — `resume` в первом RESIZE, relay — в пере-OPEN; `everConnected`/`everOpened`), агент вместо `link.snapshot()` шлёт `link.screen()` — только видимый экран со стиранием. Старый агент пометку не знает и шлёт снимок, как раньше.
- Вывод, пришедший мосту до отправки захвата, tmux уже применил к панели — он внутри снимка, и мост его не доигрывает (`early` в `bridge.ts`); через relay это окно до 700 мс. Не дошёл снимок (отказ, срок) — ранний вывод идёт клиенту сам.
- Зритель (`passive`): гость relay без права ввода открывает терминал с флагом tmux `attach -f ignore-size` и размера окна не задаёт вовсе — ни подключением, ни просьбой, ни заявкой (иначе последний подключившийся control-клиент сжимал окно владельцу до своих 80×24). Его RESIZE до терминала доходит: в режиме attach по нему рисуется его собственный pty. Проверено живым тестом на tmux 3.7c.
- Тело RESIZE проверяет `parseSize` (`pty-common.ts`): объект с числовыми `cols`/`rows`. JSON `null` — законное тело, и обращение к его полям роняло обработчик сообщения LAN, а с ним весь агент.
- pty вышедшего клиента tmux отпускается явно (`handleExit` → `killChild`): при чтении на паузе конец потока никто не читал, и master оставался открытым. После закрытия потока pty запись и смена размера по сохранённому номеру fd запрещены (`fdClosed` в `pty-spawn.ts`) — номер мог достаться другому pty.
- Срок ответа на команду (10 с) запись из очереди НЕ убирает: ответы адресуются порядком отправки, и опоздавший блок обязан достаться своей команде (`Pending.settled`), иначе сопоставление сдвигается навсегда.
- Зеркало (чужой размер панели) вписано в контейнер CSS-масштабом, а xterm о нём не знает — мышь пересчитывает `mirror-mouse.ts` (перехват на документе в фазе capture и повтор события с координатами немасштабированного экрана).
- Режим подключения помнится по сессиям (`sessionTerminalMode` в `term-mode.ts`): окно настроек, открытое из терминала, называет режим именно его сессии; расхождение с просьбой терминал говорит один раз (`term.modeOverridden`).

## Лента агента: транскрипты

Лента берётся не с экрана, а из транскрипта, который агент и так пишет на диск. Путь пройден целиком: определитель панели, чтение обоих форматов страницами по обоим транспортам и экран ленты (в чат-сессии — вид «Чат», см. ниже) — с поиском и переходом к месту.

### Определитель панели

- `packages/agent/src/agent-transcript.ts` — `resolve(pane, sources?)` отвечает, какой агент работает в панели tmux и где лежит файл его беседы; интерфейса и чтения самих транскриптов здесь нет. Отказ всегда назван причиной: `no-agent`, `unknown-format`, `no-transcript` (агент есть, беседы на диске ещё нет), `lookup-failed` (посмотреть не удалось или панели уже нет).
- Наружу отданы ещё и `codexMeta(head) -> CodexMeta{root,started,thread,forkedFrom}`, `CODEX_SESSIONS_DIR`, `HEAD_BYTES`, `clearCache()`: разбор `session_meta` один на весь агент, второго ему быть не должно.
- Три способа привязки: реестр Claude `~/.claude/sessions/<pid>.json` по полю `tmux`; открытые файлы процесса панели и потомков для Codex (`lsof`); клиент `claude attach <id>` в панели — единственное место, где читаются аргументы процесса, и берётся он, только если аргумент начало ровно одной сессии реестра.
- Codex с общим демоном (`codex app-server`): клиент в панели тонкий, файлы бесед всех потоков открыты у демона, поэтому ни открытые файлы, ни рабочий каталог панели друг от друга не отличают. Первым пробуется привязка по названию (`codexByTitle`): заголовок панели без индикатора равен названию ровно одного корневого неархивного потока её каталога в базе состояния Codex — `packages/agent/src/codex-state.ts`, `~/.codex/state_<N>.sqlite`, таблица `threads` (`name`, `rollout_path`, `cwd`, `thread_source`). Файл из базы берётся, только если он лежит в каталоге сессий и его `session_meta` корневой. Ноль или несколько совпадений, незнакомая схема, сбой — прежний путь. Замер 12.11.2026: три сессии Codex в одном каталоге — без привязки одна получала чужой поток (расход 93 млн вместо 211 млн), две отвечали `lookup-failed`; с привязкой суммы сошлись с `tokens_used` самого Codex.
- На Linux открытые файлы и каталог процесса читаются из `/proc` (`procOpenFiles`, `procCwd`), а не через `lsof`: в зависимостях агента его нет, и на сервере без него определитель был слеп целиком. `ps` зовётся с `LC_ALL=C`: время старта macOS печатает по локали («четверг, 29 октября 2026 г.»), и агент, запущенный из русского терминала, терял всю таблицу процессов.
- Порядок ответа: живой агент панели → корневой поток Codex → подключённый клиент → запись реестра, пережившая своего агента (только если панель не моложе записи, `live: false`). Порядок важен: адреса панелей переиспользуются новым сервером tmux, и мёртвая запись иначе отдала бы чужую беседу.
- `packages/agent/src/tmux-run.ts` — единственное место, где запускается tmux и распознаётся «сервера нет» (`runTmux`, `isNoServerError`, `TmuxError`); `sessions.ts`, определитель и лента ходят через него. `doctor.ts` пока зовёт tmux своим `execFile` — известное расхождение.
- Транскрипт Claude лежит в `~/.claude/projects/<cwd, где всё вне [A-Za-z0-9] заменено дефисом>/<sessionId>.jsonl`; у Codex — `~/.codex/sessions/<ГГГГ>/<ММ>/<ДД>/rollout-<ISO>-<threadId>.jsonl`, и корневой поток узнаётся по первой строке `session_meta` (нет `parent_thread_id` и `source.subagent`).
- Цепочки файлов у Claude нет намеренно (D01): продолжение и форк сессии копируют прежнюю беседу в новый файл целиком, поэтому текущий файл и есть вся беседа.
- Проверено на живых данных 14.09.2026: все 12 панелей владельца разведены верно за 0,8 с вхолодную (7 Claude, 4 Codex, одна — «беседы ещё нет»).

### Страница беседы

- `packages/agent/src/transcript-feed.ts` — `readFeed(file, agent, opts?) -> Promise<FeedPage | FeedFailure>`, `parseLine(line, agent, offset?) -> FeedEntry | null`, плюс общие для склейки `limitOf`, `weigh`, `RESPONSE_LIMIT`.
- `FeedEntry {id, at, kind: 'human'|'agent'|'thinking'|'tool'|'note', text, tool?, note?: 'compacted'|'interrupted'|'error'|'chain', branch?, truncated?, cursor?}` — одна форма на оба формата, различие остаётся полем `agent` страницы.
- `cursor` у записи — её собственная точка прыжка («<inode>:<offset>», та же форма, что принимают `before`/`after`/`around`): экран ищет по тексту и прыгает к найденному через `around(entry.cursor)`. Ставит его страница, `parseLine` не ставит — он разбирает строку в отрыве от файла. Веха `chain` от `session-feed` курсора не несёт.
- `branch` на сегодняшних данных пуст всегда: записей `isSidechain` 0 из 83 175, беседы подагентов Claude лежат отдельными файлами `…/subagents/agent-*.jsonl`, которых лента не читает.
- `FeedPage {ok:true, agent, entries, head, tail, bof, eof, skipped}`; `FeedFailure {ok:false, reason: FailureReason|'cursor-stale', detail}` — четыре слова причин импортированы из определителя, своей копии нет.
- `FeedOptions {limit?, before?, after?, around?}`: курсоры взаимоисключающие, старшинство `around` → `before` → `after`; лимит по умолчанию 200, максимум 1000.
- Курсор — `<inode>:<offset>`. Чужой inode, неразобранная строка или смещение за концом файла (файлы только дописываются) дают `cursor-stale`; цепочку файлов проверяет вызывающий, здесь виден ровно один файл.
- Файл целиком не читается никогда: окно от края растёт удвоением с 256 КиБ до 4 МиБ, пока не наберёт записей.
- Пределы: текст записи 64 КиБ с `truncated` (замер на 11 643 репликах: 8 КиБ резали 0,94 %, 64 КиБ — 0,02 %), весь ответ — 1 МиБ, аргумент в строке «что сделал» — 200 знаков.
- Замер на живых данных: хвост файла Claude 28,5 МБ — 200 записей за 37 мс; rollout Codex 94 МБ — 9 мс.
- `note: 'chain'` в типе есть, но `readFeed` его не выдаёт: веха стыка файлов принадлежит `session-feed`.

### Лента сессии

- `packages/agent/src/session-feed.ts` — `sessionFeed(session, opts?, sources?) -> Promise<FeedResult>`, где `FeedResult = (FeedPage & {complete, live}) | FeedFailure`: `complete` и `live` приклеиваются из ответа определителя, без пересчёта.
- Шов один: `SessionFeedSources {home, socketName?, activePane(session), resolve(pane), sessionFiles(dir)}` — живой tmux, определитель и обход каталога Codex подменяются здесь и только здесь.
- `socketName` по умолчанию НЕ подставляется (как у `resolve` и `SessionService`) — передавать `config.TMUX_SOCKET`, иначе запрос уйдёт на сокет tmux по умолчанию.
- Только чтение: адрес активной панели берётся `display-message`, в панель не уходит ни `send-keys`, ни переключения экрана — полноэкранный режим приложения запрос ленты не трогает.
- Цепочка форков Codex идёт только назад (`forked_from_id`); родитель ищется по `threadId` в имени файла `~/.codex/sessions/**`, обход — не чаще раза на запрос и только когда страница дошла до границы файла. Имя файла не доказательство: файл берётся, лишь если поток в его `session_meta` тот самый.
- `after`, упёршийся в конец файла-родителя, отдаёт `eof` и цепочку не тянет: новые записи пишутся только в текущий файл.
- Предел глубины — 10 файлов (защита от цикла в чужих данных): упёрлись — `bof: false` и веха `chain`, начало беседы не обещается. Веха ставится, только если за ней поехали записи родителя.
- Курсор переносит ленту через границу файлов: выданный на родителе, он на родителе и читается, а `cursor-stale` остаётся ровно тогда, когда такого файла нет во всей цепочке.

### opencode (ADR 0032)

- Беседы opencode 2.2 — не файлы, а строки одной SQLite-базы `~/.local/share/opencode/opencode.db` общего фонового сервера (`session_v2`, `session_message`); TUI в панели ни файла, ни базы не держит, поэтому `lsof` тут бесполезен.
- Привязка панели — по рабочему каталогу клиента (`opencodeThread` в `agent-transcript.ts`): последняя тронутая корневая беседа каталога. Второй клиент в том же каталоге → `lookup-failed`, беседу не трогали с запуска клиента → `no-transcript`, незнакомая схема → `unknown-format`. Ответ определителя несёт `session` рядом с путём базы.
- `packages/agent/src/opencode-db.ts` — путь базы (XDG), открытие только на чтение через ленивый `import('node:sqlite')`, распознавание ошибки схемы; `opencode-feed.ts` — `readOpencodeFeed(db, session, opts)`, курсор `<беседа>:<seq>`; разбор строки — `fromOpencode` в `transcript-feed.ts` рядом с двумя другими форматами.
- Ответ модели пишется в одну растущую строку: недописанная строка в конце беседы в ленту не идёт, курсор стоит перед ней.
- `readFeed` принимает только `FileAgent` (`claude`/`codex`) — базу opencode им не прочитать.

### Оба транспорта

- `packages/agent/src/feed-request.ts` — один разбор запроса на LAN и relay: `FeedReader = (session, opts) => Promise<FeedResult>`, `feedSession(raw) -> string`, `feedPage(read, raw) -> Promise<FeedResult>` (не бросает: неожиданный сбой даёт `{ok:false, reason:'lookup-failed'}` одинаково там и там). Пустое значение параметра равносильно отсутствующему на обоих транспортах.
- `GET /api/feed?session=&limit=&before=&after=&around=` под cookie-auth → всегда 200 с телом ленты; отказ едет полем `ok:false`, а не кодом HTTP.
- `FrameType.Feed = 46` / `FeedResult = 47`: запрос `{session, limit?, before?, after?, around?}`, ответ — то же тело без обёртки, на канале запроса. Корреляции по идентификатору нет: клиент шлёт по одному запросу за раз.
- `AgentServer({feed?})` и `RelayLink({feed?})` принимают `FeedReader`; по умолчанию `sessionFeed(session, opts, {socketName: this.socketName})`.
- `RelayLink.ownsSession(s, session, withBuild)` — единственный предикат «чья это сессия»: `doList(false)`, `doOpen(true)`, `doFeed(false)`. Гостю сборочная сессия ленты не даёт; чужая сессия — `Error {code:'forbidden'}`, и лента при этом не читается вовсе. Своя сессия открыта гостю без права `write` и без права `files`.
- Типы тела (`FeedEntry`, `FeedPage`, `FeedResult`) лежат в пакете агента, не в протоколе; в `@termhub/protocol` их так и не понесли — веб объявил свою копию формы провода в `api.ts` (см. ниже).

### Экран в приложении

- `packages/web/src/feed.ts` — `mountFeed(host, session, transport) -> {el, searchSlot, entries(), loadOlder(), jumpTo(cursor), teardown()}` и чистая `searchFeed(entries, query) -> FeedHit[]`; отдельного модуля поиска нет, он живёт тем же файлом.
- `Transport.feed(session, opts?) -> Promise<FeedResult>` — один вызов на оба транспорта: LAN в `api.ts` (`GET /api/feed`), relay в `relay-transport.ts` (кадр `Feed`). Какой транспорт под ним, экран не знает.
- Типы ленты (`FeedEntry`, `FeedPage`, `FeedFailure`, `FeedOptions`, `FeedResult`) объявлены в `api.ts` и реэкспортированы из `transport.ts`: веб знает форму провода, а не типы пакета агента — дублирование намеренное.
- `feedQuery(session, opts)` в `api.ts` — один перечень параметров на оба провода (LAN раскладывает в строку запроса, relay шлёт тем же телом кадра), поэтому новый параметр не теряется молча на одном из них; пустое значение не отправляется вовсе.
- `FeedFailureReason` веба — пять причин ленты плюс `forbidden`; то же слово добавлено в `FeedFailure` агента (`transcript-feed.ts`), хотя `readFeed` его не выдаёт: ставит его только мост relay.
- Отказ гостю едет кадром `FeedResult{ok:false, reason:'forbidden'}`, а не общим `Error` (ADR 0030): тем же `Error` гость получает отказ ещё на девять запросов контрольного канала (caffeinate повторяется раз в 3 с), и лента приняла бы чужой отказ за свой. Клиент `Error` ответом ленты не считает вовсе.
- Кадр `Feed` пропускается гостю без прав `write` и `files` (лента ничего не меняет, произвольного пути через неё не прочитать); «только своя сессия» проверяет `doFeed` — на гейте payload ещё не разобран.
- Relay: запрос ленты один в полёте, прочие ждут в `feedQueue`; срок ответа — общий `LIST_TIMEOUT_MS` (10 с). Сдавшийся по таймауту оставляет долг `feedOwed` со сроком `FEED_STALE_MS` (2 с) по монотонным часам: опоздавший ответ съедается долгом, просроченный долг забывается — иначе один таймаут глушил бы ленту до реконнекта.
- Экран тоже держит очередь (`chain`), один запрос за раз. «Занято» ответом не бывает: вторая просьба `loadOlder()` ждёт ту же подкачку и получает её итог — `true` (дочитал, начало впереди), `false` (начало беседы), `null` (экрана больше нет, за край принимать нельзя).
- Дочитывание назад крутится дальше, пока страница пуста, а курсор `head` сдвинулся: остановка — только `bof` или курсор, переставший двигаться. Это и есть правило «край — `bof`/`eof`, а не пустой список» в коде.
- `cursor-stale` лечится молча и ровно один раз на действие (`staleRetried`) — хвостом, взятым заново; второй такой ответ показывается как сбой.
- Сбой одного запроса загруженную беседу не стирает: `errorScreen` с «Повторить» ставится только на пустом экране, иначе отказ говорит строкой.
- Приращение — `after: tail` раз в 3 с и только при четырёх условиях сразу: агент жив (`live`), вкладка активна (`.th-ws-view.is-active`), страница видима и очередь пуста (ADR 0028).
- Прокрутка тянет оба края: вверх — предыдущие, вниз — продолжение, пока `eof` ложь (так бывает после прыжка к находке). «Или-или» оставило бы хвост недостижимым на беседе короче экрана, где близки оба края сразу.
- Подсветка (`is-hit`, 2 с) отмечает всю группу записей с одним курсором: агент даёт курсор строке транскрипта, а не записи. Ведут к первой видимой записи группы, а если всю группу спрятал тумблер мышления — одну показывают насильно, не трогая выбор тумблера.
- Мышление скрыто по умолчанию (у Codex оно пустое всегда), выбор живёт в `localStorage` под `termhub.feedThinking`.
- Поиск: мгновенно по загруженному, не нашлось — дочитывает назад до 20 страниц с паузой набора 300 мс, показывая счёт просмотренных; кнопка «искать дальше» даёт ещё столько же (ADR 0029). Находкой становится только запись с курсором — прыгать иначе некуда, и веха склейки в находки не попадает.
- Поколение поиска: новый запрос и замена окна (прыжок к находке, хвост заново) обесценивают идущее дочитывание — иначе его страницы засчитались бы чужому слову. После замены окна снимок пересобирается по памяти, в сеть за это не лезут.
- Размеры экрана: страница 100 записей, «у верха» 200 px, «внизу» 100 px, строка находки 120 знаков.
- Вкладка и маршрут: `sfeedHash(session)` = `#/sfeed/<session>` в `routes.ts`, `WsTab 'feed'` в `workspace.ts`. Отдельной кнопки «Лента» в полосе разделов больше нет: у сессии с чатом вид переключается в плашке «Терминал» (`renderHoloBar`, `ui.ts`, `view-pref.ts`).
- Существование вкладки решает `whenCap('feed', transport)`: у старого агента её нет вовсе, и прямая ссылка уводит на терминал, а не показывает пустой экран. Гостю без права `files` лента видна — в отличие от проводника и репозитория.
- Строки — секция `feed.*` и `holo.feed` в `i18n.ts`; стили — `.th-feed*` в `theme.css`.
- `[hidden] { display: none !important }` — одно правило в начале `theme.css` на всё приложение: собственный `display` кнопки или полосы иначе перебивает атрибут, и элемент висит на экране вопреки коду. Поштучные обходы в `tabs.ts` и `dashboard.ts` сняты, новых не заводить.

## Чат: нативный интерфейс к агентам

Чат — экран к Claude Code и Codex в панели tmux: переписка из транскрипта (раздел «Лента»), живое состояние и действия — с экрана панели. Разбор замеров — `docs/native-agent-ui.ru.md`, слова — `CONTEXT.md`, решения — `docs/adr/0038`–`0045`.

- Откуда что: история — транскрипт (ADR 0038); «работает / вопрос / режим / строка ввода» — экран панели; транскрипты не хранят цветов вывода, поэтому раскраска оболочки и дифф рисуются на клиенте (`chat-color.ts`).
- Формы провода — `packages/protocol/src/chat.ts` (подпуть `@termhub/protocol/chat`, без крипты): `ScreenState`, `LiveState`, `ChatAction`, `ActResult`, `ChatCommand`, `ToolDetail`; отпечаток вопроса считает одна `questionStamp`.
- Агент: `agent-profiles.ts` (профили Claude и Codex как данные: клавиши, режимы, признаки экранов, проверенные версии, ADR 0041), `agent-screen.ts` (чистые `readScreen`/`readPopup`/`readPending`), `pane-io.ts` (`capturePane`/`sendKeys`/`pasteText` вне `Link`), `agent-live.ts` (`sessionLive`/`sessionAct`, шов `LiveSources`), `agent-commands.ts` (список «/»-команд, сверка с окном агента, кэш `~/.termhub/commands-<агент>-<версия>.json`), `chat-request.ts` (один разбор на оба транспорта, не бросает).
- Правки в старом: `transcript-feed.ts` (`readDetail`, `detail`/`desc`/`outcome` у записей), `transcript-usage.ts` (`context`), `paste-image.ts` (`name`, любой тип до 50 МиБ), `files.ts` (чтение картинок для чата).
- Провод LAN: `GET /api/live?session=`, `POST /api/act`, `GET /api/commands?session=`, `GET /api/feed?…&detail=<cursor>`, `GET /api/files/image?session=&path=`, `POST /api/paste-image?type=&name=`. Отказ — всегда 200 с `{ok:false, reason, detail}`.
- Провод relay: `Live = 48`/`LiveResult = 49`, `Act = 50`/`ActResult = 51`, `Commands = 52`/`CommandsResult = 53` (несут `id`, очереди «один в полёте» нет), поле `detail` кадра `Feed`, действие `image` и `paste-chunk` с `name` кадра `FileOp`. Возможность `chat` (`CAP_CHAT`): без неё веб ничего из этого не шлёт.
- Права гостя: `Live`, `Feed`, `Commands`-чтение — только своя сессия; `Act` и вставка — `write`; чужая сессия — `forbidden`. Картинки гостю — только каталог его сессии и единый отказ `image unavailable`.
- Временный каталог агента (`/tmp/claude-<uid>`) отдаётся владельцу целиком, гостю — нет; в `FileService` каталоги — `agentTempDirs`.
- Причины отказа действий: слова ленты плюс `stale` (экран уже другой), `busy`, `unsupported`; тот, кто ответил `ok`, должен дойти до экрана: ответ, не подтверждённый экраном (2,4 с тот же вопрос или неузнанный), — `stale`.
- Веб: `chat.ts` (оболочка поверх `mountFeed`), `chat-live.ts` (опрос экрана, карточка вопроса, «Стоп», режим, модель), `chat-composer.ts`+`chat-complete.ts` (ввод, «/» и «@»), `chat-term.ts` (окошко терминала), `chat-health.ts` (счётчик неузнанных экранов), `chat-view.ts`, `chat-images.ts`, `view-pref.ts` (`termhub.sessionView`, `effectiveView`). Тесты — `packages/web/test/chat-*.test.ts`, `view-pref.test.ts`.

## Расход по сессиям (ADR 0033)

- `packages/agent/src/transcript-usage.ts` — `readUsage(file, agent, now?) -> UsagePage | FeedFailure`: токены (`input`, `cached`, `cacheWrite`, `output`), число ответов и время работы — всего и за локальный «сегодня». Claude считается по одному разу на `message.id`, Codex — разностью нарастающих итогов `token_count`. Файл читается целиком один раз, дальше только хвост (кэш по пути, inode, смещению).
- `sessionUsage(session, sources?, now?)` в `session-feed.ts` делит с лентой шаг `locate` (сессия → панель → файл беседы); opencode отвечает `unknown-format`.
- Провод — флаг `usage` запроса ленты (`GET /api/feed?…&usage=1`, поле `usage` кадра `Feed`), ответ тем же `FeedResult`; своего кадра нет. Разбор флага — `feedPage(read, raw, usage?)` в `feed-request.ts`; `AgentServer({usage?})` и `RelayLink({usage?})` принимают `UsageReader`.
- Возможность `CAP_USAGE = 'usage'`: без неё веб расход не спрашивает (старый агент ответил бы страницей ленты).
- Память сессии — `packages/agent/src/session-memory.ts`: `sessionMemory(session, sources?)` — сумма RSS по дереву процессов от корней всех панелей сессии (`list-panes -s`, `ps -axo pid=,ppid=,rss=`, таблица кэшируется на 2 с), байты; оценка сверху — общие страницы посчитаны у каждого процесса. `sessionUsage` приклеивает поле `memory` и к расходу, и к отказу: у сессии без агента токенов нет, а память есть. Окно расхода показывает такие сессии строкой с прочерками; нет поля — прочерк в колонке (агент старше или не посчитал).
- Проверки Guardian (Codex): отдельные потоки `thread_source = 'guardian_review'` со своим расходом. В базе состояния они с родителем не связаны (только общий каталог) — связь стоит в `session_meta` файла проверки (`session_id`, `parent_thread_id`). `codexReviewFiles(home, rolloutPath)` в `codex-state.ts` отдаёт файлы проверок потока, `readReviewsUsage` их суммирует, `sessionUsage` приклеивает поле `reviews {count, total, today}` — в `total`/`today` беседы оно НЕ входит. Окно расхода показывает его строкой `.th-usage__sub` под сессией и включает в итог. Замер 12.11.2026: 21, 17 и 10 проверок на 33, 32 и 22 млн токенов.
- Веб: `packages/web/src/usage.ts` — `sessionUsage(transport, session)` поверх `Transport.feed(session, {usage: true})` и окно `openUsage(transport)` (меню дашборда и палитра). Ожидаемое тело — `USAGE_PAGE`/`USAGE_PAGE_JSON` в `feed-fixture.ts`, общее для LAN и relay. Счётчик той же сессии стоит в шапке экрана ленты (`.th-feed__usage`): сегодня — текстом, вся беседа — в подсказке, обновление раз в 30 с при видимой вкладке.

## Вид, навигация и обзор (веб)

- `packages/web/src/term-prefs.ts` — вид терминала в `localStorage`: размер и семейство шрифта, межстрочный интервал, фон (`soft`/`contrast`, один выбор на обе темы), автоскрытие полосы разделов, боковые вкладки. Атрибуты на `:root` (`data-term-bg`, `data-holo-auto`, `data-side-tabs`) — раскладку и краски держит `theme.css`; открытый терминал слушает `onTermPrefsChange`. Окно — `term-settings.ts` (см. «Настройки» ниже).
- Своей цветовой схемы у терминала нет: он идёт за темой приложения (`setThemeChoice` в `theme.ts`). В светлой теме xterm получает `minimumContrastRatio: 4.5` — агенты красят вывод под тёмный терминал.
- Панель клавиш (`quickkeys.ts`) — два ряда: клавиши (Esc, Tab, стрелки, Enter справа; на телефоне одной строкой) и второй — ⇧Tab и ⇧← слева (`second` в `SEND_KEYS`), за ними инструменты (выделение, поиск, тумблеры клавиатуры и строки ввода). Удержание кнопки шлёт другую последовательность (`holdOf` в `SEND_KEYS`, `HOLD_MS`): Esc → Ctrl+C, Enter → Shift+Enter (перенос строки, ESC+CR); отдельных кнопок у них нет. Размер шрифта и выбор «Enter отправляет / переносит» — в окне настроек.
- Горячие клавиши живут в `mountSessionTabs` (capture на `document`): `Ctrl+Alt+1…9` — вкладка по номеру, `Ctrl+Alt+←/→` — соседняя, `Ctrl+Alt+↓` — следующая ждущая, `Ctrl+Alt+K`/`⌘K` — палитра (`palette.ts`). Голый `Ctrl+K` не занимать: это «стереть до конца строки» в оболочке.
- Очередь ждущих (`.th-tabs-queue`) — счётчик `bellUnseen` без текущей сессии; источник тот же, что у 🔔.
- Вид сессии один на три места — `packages/web/src/session-view.ts`: `syncSessionHead(host, prefix, info, t, showActivity)` строит и обновляет на месте «шапку сессии» (метка агента, точка активности, заголовок и tmux-имя второй строкой, звонок). Вкладка (`th-tab`, компактно) показывает только её; карточка главной и панели по стрелке (`th-card`) — её же плюс каталог, превью, состояние и подвал. Элементы несут общий класс `th-sess__*` и свой `<prefix>__*`; второй разметки имени сессии не заводить.
- Группы по проектам тоже общие: `groupSessions`/`sessionGroup` и заголовки `syncGroupHeaders`/`clearGroupHeaders` (класс `.th-group`) — в боковой панели, в панели по стрелке и на главной; в полосе вкладок сверху заголовков нет. Одна группа на весь список — заголовка нет.
- Метка агента — элемент `.th-tab__agent` с буквой и подсказкой (`AGENT_MARK` в `session-view.ts`), цвет — по её собственному `data-agent`; агент узнаётся по команде панели (`sessionAgent` в `session-status.ts`: Claude называет процесс номером версии). Бейдж подвала карточки называет агента, а не команду. Цветная черта была и читалась как «ждёт реакции» — не возвращать.
- Меню (`buildMenu` в `ui.ts`) собирается группами в одном порядке: беседы (поиск, расход) · настройки · агент и связь (уведомления, сон, сведения о подключении) · доступ (устройства, поделиться). Раскладка `menu` — всё под «⋯» (главная), `bar` — частое рядом иконками, редкое под «⋯» (шапка сессии в боковом режиме). `strip` — все действия одним рядом без «⋯»: полоса `.th-spanel__tools` под шапкой окна сессий (на телефоне в шапке сессии этим кнопкам нет места; в боковом режиме на десктопе полосу прячет CSS). Пункт, зависящий от возможности агента, стоит на месте скрытым и показывается ответом обмена. Иконки не повторяются: расход — `chart`, сведения о подключении — `info`, настройки — `gear`, глобус — только связь и выбор сервера.
- Настройки — одно окно на всё приложение (`openTermSettings` в `term-settings.ts`, шестерёнка в шапке и в меню): вид (тема, шрифт, интервал, фон терминала), раскладка на десктопе, ввод (`enterSends` — что делает Enter), подключение (control mode или attach) и язык. Отдельных пунктов темы и языка в меню нет. Всё, кроме языка и темы, хранит `term-prefs.ts`.
- Сведения о подключении — окно `openDiag()` поверх экрана; страница `#/diag` осталась только для прямой ссылки.
- Сплит-вид: `#/split/<a>/<b>[/…]` (до четырёх), `split.ts`; панель — `mountTerminal(…, {embedded: true})`: без шапки, полосы разделов и панели клавиш, свой канал на сессию.
- Боковая панель — та же полоса `.th-tabs`, переложенная CSS в столбец (`data-side-tabs`, только десктоп); группы — `sessionGroup` (имя без хвостового номера).
- Превью на карточках — `session-preview.ts`: последняя реплика из ленты, не чаще раза в 10 с на сессию и только при возможности `feed`.
- Поиск по всем лентам — `feed-search-all.ts`, на клиенте: до 5 страниц по 200 записей с хвоста каждой беседы; прыжок к находке передаётся через `setFeedJump`/`takeFeedJump`, адрес ленты курсора не несёт.

## Вставка из буфера и картинки агенту (ADR 0037)

Агент в панели читает буфер хоста (Ctrl+V у Claude Code и Codex), а картинка лежит в буфере устройства с браузером. Поэтому картинка загружается на хост, а в терминал вставляется путь файла — оба агента превращают вставленный путь картинки во вложение.

- `packages/agent/src/paste-image.ts` — `PasteStore`: каталог `~/.termhub/paste` (0700, файлы 0600), имя `paste-<время>-<хвост>.<ext>` выбирает агент, клиент называет только тип (png/jpeg/gif/webp); предел 20 МиБ, файлы старше 7 дней убирает следующая вставка. `saveStream` — LAN, `chunk` — relay.
- Провод: LAN — `POST /api/paste-image?type=<mime>` (тело — файл) → `{path}`; relay — действие `paste-chunk` кадра `FileOp` (`{upload, type, offset, last, data}`), путь в ответе на последний кусок. Своего кадра и возможности нет: старый агент отвечает ошибкой, и веб показывает её тостом.
- Права гостя relay: `paste-chunk` требует `write` (как ввод), а не `files`. Гейт пускает `FileOp` с любым из двух прав, оба проверяет `doFileOp`; прочие файловые действия без `files` получают отказ `no files permission`.
- Веб: `packages/web/src/term-paste.ts` — `readClipboard()` (картинка старше текста; `unavailable` вне защищённого контекста, `denied` при отказе), `imageFromPaste`, `pathForPaste`; `Transport.pasteImage(blob) -> путь`. В `term.ts` три входа: кнопка «Вставить из буфера» во втором ряду панели клавиш (сразу за ⇧Tab и ⇧←; текст — `term.paste`, картинка — загрузка), событие `paste` с картинкой без текста (Cmd+V, меню браузера) и Ctrl+V — читается буфер устройства: есть картинка — загрузка, иначе в терминал уходит обычный `^V`.
- Тесты: `packages/agent/test/paste-image.test.ts`, близнецы в `server.test.ts` и `relay-link.test.ts`, `packages/web/test/term-paste.test.ts`, кнопка — в `quickkeys.test.ts`.

## Установленное приложение: окно без заголовка и меню иконки

- Манифест (`packages/web/public/manifest.webmanifest`): `display_override: ["window-controls-overlay"]` — в Chrome и Edge на десктопе полоса заголовка отдаётся странице (включает пользователь стрелкой в заголовке окна). Раскладка — один блок `@media (display-mode: window-controls-overlay)` в `theme.css`: шапки (`.th-header`, `.th-termbar`, `.th-spanel__head`) отступают от кнопок окна (`--wco-left`/`--wco-right` из `env(titlebar-area-*)`). Блок стоит в конце файла — выше его отступы перебивались собственными правилами шапок. Окно перетаскивают только за пустые места шапки: отдельные элементы без кнопок внутри (`.th-header::after`, `.th-tabs::after`, `.th-tabs-current`, заголовки сплита и окна сессий). Шапку целиком областью перетаскивания НЕ помечать: область захватывала потомков вне её границ (столбец вкладок бокового режима) и с ним весь экран — вкладки не нажимались, окно таскалось за терминал. Новая шапка у верха экрана обязана попасть в этот блок, иначе она ляжет под кнопки окна. Safari режим не знает — там обычный заголовок.
- Меню иконки (Dock, панель задач) — поле `shortcuts`: адреса `./#/do/<действие>`, список действий — `packages/web/src/app-actions.ts` (`new`, `usage`, `settings`). Это не экран: `main.ts` запоминает действие, возвращает прежний адрес и открывает окно поверх текущего экрана (`runPending`); действие, которому не на чем выполниться (нет связи, экран входа), ждёт `ACTION_WAIT_MS`. `launch_handler: focus-existing` — пункт меню поднимает открытое окно, действие приходит через `launchQueue`; без поддержки открывается новое окно с тем же адресом. Строки манифеста статичны и в i18n не входят. Системное меню macOS и меню «⋯» Chrome странице недоступны.
- Тесты: `packages/web/test/manifest.test.ts` (каждый адрес `shortcuts` разбирается в известное действие), `packages/web/test/app-actions.test.ts`.

## Не спать при закрытой крышке (ADR 0036)

Пользовательское описание — `docs/lid-awake.ru.md` / `docs/lid-awake.md` (держать синхронными).

- `packages/agent/src/lid-awake.ts` — `LidAwake`: системная настройка `SleepDisabled` через `sudo -n /usr/bin/pmset -a disablesleep 1|0` (механизм Fermata, но штатной командой). Только macOS. Права — правило sudoers на ровно две команды; его печатает `termhub lid-awake` (`runLidAwake` в `cli.ts`), выполняет владелец. Наличие разрешения — по списку правил `sudo -n -l` (`allowsWithoutPassword`: обе команды в строке NOPASSWD), перепроверка раз в 15 с; вопрос про одну команду врёт, как только у пользователя есть любое правило NOPASSWD.
- Режим снимается сам: крышку закрыли и открыли (`checkLid`, опрос `ioreg -r -k AppleClamshellState` раз в 2 с), остановка агента (`release`), старт после падения (`recover` по метке `~/.termhub/lid-awake.on`). Включённый при открытой крышке ждёт закрытия.
- Провод — прежний кадр `Caffeinate` / `POST /api/caffeinate`: запрос `{active?}` или `{lid?}`, ответ `{active, supported, lidSupported?, lidReady?, lid?}`. Тело собирает `Caffeinate.state()`, запрос применяет `Caffeinate.apply()` — оба транспорта зовут их, своей сборки тела не держат. Новой возможности нет: старый агент на `{lid}` отвечает прежним состоянием.
- Веб: `Transport.setLidAwake(on)`; кнопка — `addCaffeineItem` в `ui.ts`: нажатие — обычный режим, удержание `LID_HOLD_MS` — режим крышки (только при `lidSupported`); пока режим крышки включён, любое нажатие его выключает, класс `is-lid` мигает жёлтым, пока режим включён идёт опрос раз в 5 с (хост снимает режим сам). Каждое переключение и автоснятие — тостом; отказ хоста (нет разрешения) — тост про `termhub lid-awake`.
- Тесты: `packages/agent/test/lid-awake.test.ts` (команды подменены — настоящий `sudo`/`pmset` не зовётся), близнецы в `server.test.ts` и `relay-link.test.ts`, `packages/web/test/lid-awake.test.ts`.

## Локальные входы агента

- `tlsExtra` в config.json — дополнительные сертификаты, выбираемые по имени запроса (`SNICallback` в `server.ts`); основной сертификат старше. `termhub local-cert` (`local-cert.ts`) выпускает через `openssl` свой центр, ограниченный именами localhost/127.0.0.1/::1 (`nameConstraints`), и лист на 800 дней — с тем же типом ключа, что у основного сертификата (при ECDSA-основном RSA-лист в TLS 1.3 не отдаётся вовсе, агент о несовпадении предупреждает в логе); доверие центру выдаёт владелец командой, которую CLI печатает.
- `localHttpPort` — второй вход, обычный HTTP только на 127.0.0.1 (адрес привязки не настраивается): `http://localhost` браузеры считают защищённым контекстом. Занятый порт агента не роняет.
- Кука получает `Secure` по соединению (`req.socket.encrypted`), а не по наличию `tls` в конфиге — иначе вход по паролю на HTTP-входе не работал бы в Safari.
- Тесты — `packages/agent/test/local-entrance.test.ts` (настоящий `openssl` во временном каталоге).

## Свой relay на машине агента

Пользовательское описание — раздел в `docs/remote.ru.md` / `docs/remote.md`.

- `localRelay: {port, host?, tls?}` в config.json (`readLocalRelay` в `packages/agent/src/local-relay.ts`): поля нет — ничего не меняется. `tls` не задан — сертификат агента, `null` — обычный HTTP.
- Relay — отдельный процесс (`LocalRelay`: `fork` бинаря `@termhub/relay`, перезапуск с паузой 1–30 с, настройки через окружение `PORT`/`HOST`/`TLS_CERT`/`TLS_KEY`): он разбирает трафик из интернета, и его падение не должно ронять агента. Потеряв родителя (`disconnect` канала fork), relay выходит сам — иначе держал бы порт.
- Мостов `RelayLink` у агента теперь список (`cli.ts`): на `relayUrl` и на свой relay по loopback (`dial.insecure` — сертификат выписан на внешнее имя; из конфига флаг не читается). Статус связи в `/api/diag` — первого моста, пересечение возможностей — самого свежего обмена; свой relay — отдельным полем `localRelay`.
- Код пейринга один на все мосты (`sharePairing`): `RelayLink.openPairing(scope, preset)` принимает готовый код, ответ даёт первый открывший комнату, использованный на одном relay код снимается на остальных (`cancelPairing`). Кадр `Share` от клиента открывает пейринг только на своём мосту.
- Требование HTTPS: `RELAY_REQUIRE_HTTPS=1` / `RelayOptions.requireHttps` / `localRelay.requireHttps`. Со своим TLS выполнено само; за прокси нужен `X-Forwarded-Proto: https` от доверенного прокси (последнее значение заголовка), иначе 308 на https для GET и 403 остальному; `/healthz` открыт. Без TLS и без доверенного прокси relay не стартует. HSTS НЕ ставим: он действует на имя целиком, без порта, и сломал бы `http://localhost:7711`.
- Relay умеет TLS и адрес привязки сам (`RelayOptions.tls`/`host`); занятый порт — отказ `listen()`, а не необработанное событие.
- Тесты: `packages/agent/test/local-relay.test.ts` (процесс подменён), `packages/relay/test/tls.test.ts` (настоящий `openssl`).

## Обход удушения потока (ADR 0034)

Пользовательское описание и настройка — `docs/throttling.ru.md` / `docs/throttling.md` (держать синхронными); в `docs/remote*.md` осталась только отсылка.

Фильтр на пути к relay пропускает ~25 пакетов сервера на соединение и дальше молчит; лимит — на поток, судьбу потока решает первый пакет клиента. Три обхода, все настройкой, по умолчанию выключены.

- `packages/protocol/src/pollsock.ts` — «сокет поверх коротких запросов»: `PollSocket` (клиент, интерфейс WebSocket, только `fetch` — годится браузеру и Node), кодек потока (`encodePollMessage`, `PollDecoder`), пределы `POLL_DOWN_CHUNK` 8 КБ / `POLL_UP_CHUNK` 16 КБ. Веб тянет его из `@termhub/protocol/pollsock` — корневой экспорт несёт libsodium.
- `packages/relay/src/poll.ts` — `PollHub`/`PollConn`: серверная сторона на том же пути `/relay` (`/relay/open|down|up`). `PollConn` повторяет интерфейс `ws`, и `RelayServer.onConnection` принимает его как сокет — регистрация, комнаты и форвардинг второй ветки не имеют и иметь не должны.
- `packages/relay/src/static.ts` — режим кусков (`RELAY_CHUNKED=1`): `serveChunk` (`/_c/<i>/<путь>` — кусок 8 КБ сжатого файла), `bootIndex` (переписывает `index.html` на загрузчик), `BOOT_JS`, проба `/__sw-chunked`. Собирает куски `packages/web/src/sw-chunks.ts` в `sw.ts`; режим SW узнаёт из `/api/mode` (`chunked`), LAN-агент этого поля не отдаёт.
- `packages/protocol/src/disguise.ts` — преамбулы `ssh`/`rdp`/`dns` и `prefaceLength`; `packages/relay/src/disguise-port.ts` — порт, срезающий преамбулу (`DISGUISE_PORT`, `DISGUISE_UPSTREAM`).
- `packages/agent/src/relay-dial.ts` — единственное место, где агент и CLI открывают соединение с relay: `readRelayDial` (config.json: `relayConnect`, `relayDisguise`, `relayTransport`; окружение `TERMHUB_RELAY_*` старше) и `openRelaySocket`. Своего `new WebSocket(relayUrl)` не заводить.
- `packages/protocol/src/rtcsock.ts` — `RtcSocket`: тот же интерфейс WebSocket поверх WebRTC DataChannel; сигнализация `POST /relay/rtc {sdp} → {sdp}`, кандидаты клиента вырезаются (`stripCandidates`), по каналу идёт поток `pollsock` кусками `RTC_CHUNK` 16 КБ. `packages/relay/src/rtc.ts` — `RtcHub`/`RtcConn` на `werift` (ленивый импорт, ICE-lite, `RTC_PORT_RANGE`, `RTC_PUBLIC_IP` подставляется в кандидаты ответа — `advertise`).
- `packages/web/src/relay-socket.ts` — то же для браузера: подсказка relay (`/api/mode`, `transport`: `ws`/`poll`/`rtc`) и выбор устройства `localStorage['termhub.relayTransport']`. `rtc`, не открывшийся с первого раза, на 10 минут уступает `poll`. У агента и CLI режима `rtc` нет — им хватает маскировки.
- Живость связи в вебе (`relay-transport.ts`): мёртвое соединение не рвётся, а молчит (сон вкладки на телефоне, смена сети), и сокет числится открытым. Поэтому на возврат страницы (`visibilitychange`, `online`, `pageshow`) и на тишину дольше 15 с транспорт шлёт агенту `Ping` сквозь поток (`probe`); любой расшифрованный кадр — ответ, молчание 3 с — `dropSocket`. `dropSocket` события закрытия не ждёт (у мёртвого сокета оно приходит через десятки секунд) и сразу зовёт `onClose`. Соединение, не дошедшее до потока за 12 с, бросается так же. Тесты — `packages/web/test/relay-liveness.test.ts`.
- `RtcSocket` следит за `connectionState` соединения, а не только за каналом: `failed`/`closed` — закрытие сразу, `disconnected` — через 4 с, если браузер не починил путь сам. Откат `rtc` → `poll` после неудачи: 10 минут, если WebRTC в этой сети ни разу не открылся, и 20 секунд, если уже работал (`noteRtcOutcome` в `relay-socket.ts`).
- Способ подключения виден в трёх местах: лог relay (`agent registered … via ws|poll|rtc`, `client connected/disconnected … via …`; агент за маскировкой или туннелем для relay — обычный `ws`), `/api/diag` агента (`relay.dial` — строка `describeDial`) и окно сведений о подключении в вебе: на LAN — строка агента, через relay — способ самой вкладки (`relay-transport-state.ts`, модуль без импортов: диагностика живёт в основном бандле, сокеты — в ленивом).
- Каждый ответ коротких запросов и кусков обязан закрывать соединение; перед relay для этого нужен HTTP/1.1 без h2 и `Connection: close` (Caddy снимает hop-by-hop заголовок relay, поэтому ставит свой). В HTTP/2 всё едет одним соединением и умирает.
- Пути `/relay/*` service worker пропускает мимо кэша (`sw-strategy.ts`): это живой поток, а стратегия по умолчанию — cache-first.
- Тесты WebRTC — `packages/relay/test/rtc.test.ts`: клиентом служит тот же `RtcSocket` поверх `werift` (`opts.peer`), браузерный `RTCPeerConnection` в сюите не участвует.
- Тесты: `packages/relay/test/bypass.test.ts` (живой relay: оба транспорта в обе стороны, куски, порт маскировки), `packages/agent/test/relay-dial.test.ts`, `packages/web/test/sw-chunks.test.ts`, `packages/protocol/test/{pollsock,disguise}.test.ts`.

## Объявление возможностей (ADR 0018)

- `packages/protocol/src/capabilities.ts` — `CAP_FEED = 'feed'`, `AGENT_CAPS`, `CLIENT_CAPS`, `parseCaps(value)`, `intersect(a, b)`. Список — данные: новое имя добавляется строкой, разбор кадров и маршрутов не меняется.
- `FrameType.Capabilities = 44` / `CapabilitiesResult = 45`, payload `{caps: string[]}` в обе стороны; гостю отвечают наравне — это данные о протоколе, а не доступ к сессиям.
- LAN: `POST /api/capabilities {caps} → {caps: AGENT_CAPS}`; `GET /api/diag` отдаёт `caps: {agent, negotiated}`, где `negotiated` — пересечение с последним объявившимся клиентом независимо от транспорта (сравнение по `capsAt`). `RelayLink.status()` несёт `{caps, capsAt}` рядом с состоянием связи.
- Веб: `Transport.capabilities(caps)` у обоих транспортов; `packages/web/src/capabilities.ts` — `negotiateCaps(transport)`, `forgetCaps()`, `hasCap(name)`, `negotiatedCaps()`. Обмен один на транспорт, зовётся из `main.ts` (LAN, кроме экрана логина) и `remote.ts` (relay, по смене статуса).
- Пустым пересечение делают только 404 (агент старше маршрута) и молчание 2 с (`CAPS_TIMEOUT_MS` в `relay-transport.ts`) — это «не умеет», а не ошибка. 401 означает «обмена ещё не было» и повторяется после входа. Любой другой сбой (агент перезапускается, сеть, 5xx, relay без потока) — тоже «обмена не было»: запомненный как «не умеет», он до перезагрузки страницы прятал кнопку ленты у живого агента.
- `whenCap(name, transport)` — единственный ответ веба на «умеет ли этот агент»: ждёт идущий обмен, на отказе обмена говорит «нет». Спрашивают там и таб-бар, и рабочее пространство; второй ветки отказа не заводить.
- Состояние принадлежит транспорту: обрыв и смена агента гасят его `forgetCaps()`, иначе экран отвечал бы за прежнего агента.
- Агент хранит пересечение с последним клиентом, а не по каждому: ни один кадр этого этапа им не гейтится — кадр ленты отвечает на запрос и сам ничего не шлёт.

## Соглашения

- Логи агента — английские, формат строки `session <имя>: <что случилось>`; префикса вида `[Context]` здесь нет.
- Номера кадров только растут и не переиспользуются; занято по `CommandsResult = 53`.
- Имя возможности — часть внешнего контракта (ADR 0018): убрать или переименовать его так же дорого, как поменять сам кадр.
- Причины отказа ленты — те же четыре слова определителя плюс `cursor-stale` и `forbidden` (его ставит только мост relay); новых слов для старых причин не заводить.
- Пределы страницы (`limitOf`, `weigh`, `RESPONSE_LIMIT`) и разбор `session_meta` (`codexMeta`) существуют в одном экземпляре — второй считал бы «столько же» иначе, а на кириллице вдвое иначе.

## Подводные камни

- Web-сборка запускает Vite без `tsc`; после правок `packages/web/src/` обязательна отдельная команда typecheck выше.
- После правки `packages/protocol/src/frames.ts` обязателен `npm run build -w @termhub/protocol`: тесты вне пакета протокола импортируют его собранным.
- **Признак конца ленты — `eof`/`bof`, а НЕ пустой список записей.** Пустая страница со сдвинутым курсором означает шаг через строку, не влезшую в окно 4 МиБ (на живых данных такая есть — запись сжатия Codex 4,19 МБ); остановившись на ней, клиент потеряет всё, что за ней. Перешагивание работает в обе стороны и в `skipped` не попадает: этот счётчик означает только битые строки.
- Строка Claude с несколькими блоками даёт несколько записей (`uuid`, `uuid#1`, …) и между страницами не делится, поэтому страница бывает на пару записей шире `limit`.
- Мышление Codex приезжает с пустым текстом: summary на живых данных зашифрован.
- `display-message -p -t =имя` на несуществующей сессии отвечает кодом 0 и строкой «:.» — адрес панели поэтому проверяется регуляркой, иначе такой «адрес» ушёл бы определителю.
- Живой транскрипт весит мегабайты (7,2 МБ у идущей сессии Claude, 28,5 МБ у длинной) — целиком не читать никогда.
- Поля «продолжает вон ту беседу» у Codex нет ни в одном из 328 файлов: единственная связь форка — `forked_from_id` (51 из 248 вложенных потоков и ни один из 80 корневых).
- Реестр Claude описывает не только панели: у фоновой сессии (`kind: "bg"`) поля `tmux` нет вовсе, и найти её можно только по клиенту `claude attach <id>` в панели. Запись живёт дольше своего процесса, а `procStart` в ней записан в UTC, тогда как `ps` печатает локальное время.
- Обход открытых файлов (`lsof`) на дюжине панелей стоит 0,05–1,5 с на панель вхолодную и 0,05–0,18 с повторно (замер 14.09.2026 на нагруженной машине) — отсюда кэш на панель и срок 5 с.
- Codex preset передаёт `tui.animations=false` и `tui.terminal_title=["activity","thread-title"]` только argv нового процесса; `~/.codex/config.toml` не читается и не меняется.
- tmux-id остаётся стабильным адресом сессии; очищенный `pane_title` становится подписью таба и browser title, обновляется web-поллингом раз в 3 секунды и откатывается к tmux-id.
- Parser Claude/Codex title общий в `packages/protocol/src/session-title.ts`; web импортирует `@termhub/protocol/session-title`, чтобы корневой crypto-экспорт с libsodium не попал в LAN-бандл.
- `open-host` принимает только обычный файл внутри root после `realpath`, затем вызывает `open`/`xdg-open` отдельным argv с `shell: false`; побег, unsupported OS, spawn error и non-zero exit отклоняются.
- LAN `open-host` проходит cookie-auth и Origin-check; relay требует `scope.write` и shared-session path, а UI скрывает кнопку у read-only гостя и блокирует её на время запроса.
- При mouse tracking Codex обычный drag остаётся у TUI, а macOS Option+drag создаёт xterm selection и автокопирует его на mouseup; snapshot живёт до нового mousedown, `Ctrl+C` без selection уходит в TUI.
- Замер на живом tmux 3.7b 12.09.2026: `tmux attach` первым байтом шлёт `ESC[?1049h` и держит клиента в alt-screen до detach, поэтому локального scrollback в таком подключении нет.
- `tmux -CC` (control mode) alt-screen не шлёт и статусную строку клиенту не отдаёт; подключение стоит десятки байт без перерисовки экрана.
- Из control mode ввод идёт через `send-keys -H`, размер окна — `refresh-client -C` (держится после ухода клиента), история панели — `capture-pane -p -e -S -`, около 89 байт на строку.
- В `%output` экранированы только управляющие байты и слэш — тремя восьмеричными цифрами; битую последовательность парсер пропускает как есть: терять строку вывода хуже, а писать в лог из чистого модуля некуда.
- `%end`/`%error` закрывают блок только при совпадении номера команды — тело `capture-pane` само может начинаться с `%`; CR перед LF парсер срезает (его ставит терминальный драйвер pty).
- Пределы разборщика: строка тела свыше 1 МиБ и блок без `%end` за 100 000 строк бракуются событием `error` с номером этого блока — ждущая команда обязана быть отвергнута, а номер засчитан занятым, иначе сопоставление ответов сдвинется навсегда.
- Порядок «снимок, затем поток»: control mode экран не перерисовывает, поэтому живой вывод придерживается до конца `capture-pane`; придержание отпускают мегабайт вывода или 3 секунды, и опоздавший после этого снимок на экран уже не идёт — историю до подключения пользователь не увидит.
- Готовность control mode ждут 2 секунды, но срок заводится заново, пока протокол отвечает уведомлениями, — до общего предела 10 секунд от открытия: иначе откат сработал бы на живом control mode, где ещё просто нет номера первого блока.
- После отката служебные команды слать НЕКУДА: у attach-клиента stdin — это клавиатура пользователя, и `refresh-client -C …` уйдёт в сессию текстом.
- Альтернативный экран считается по потоку активной панели (отдельного уведомления tmux не шлёт) и узнаётся ровно по `ESC[?1049h`/`ESC[?1049l`; вариант с параметрами не распознаётся, начальное состояние даёт `alternate_on` в ответе `display-message`.
- Второй alt-screen приходит от приложения в панели, а не от tmux. Codex работает inline; **работающий Claude Code уходит в alt-screen** — прежний замер делался на свежем процессе и был неверен (проверено на живых сессиях: 7 панелей из 12, все Claude 2.1.259+). Значит в сессиях Claude истории на экране нет и листать нечего: горит пометка «Полноэкранное приложение» — ради этого случая лента и читается с диска. Запрет `alternate-screen off` на сокете агента это чинил, но отменён в тот же день (ADR 0019 → ADR 0020) — без alt-screen рамка ввода Claude становится частью потока и уезжает при листании. Опцию агент НЕ трогает: механики в коде нет, возвращать её без этапа 5 (своя строка ввода) не на что.

## Как здесь работает Autopilot

Часть работы ведётся навыком `/autopilot`. Требования, спецификация и таски —
в `.autopilot/<фича>/`. Прогресс — `.autopilot/dashboard.html`. Правило:
требование из `manifest.md` может снять только пользователь.

Если сборка прервалась — скажи «продолжи автопилот»: состояние поднимется
из `.autopilot/state.js`, переспрашивать ничего не нужно.

### Правка без автопилота

Мелкий баг или доводка после сборки — обычная сессия, без прогона.

Сначала прочитай:
1. `.autopilot/PROGRESS.md` — что не доделано, известные баги, о чём договорились с пользователем.
2. Что правили после последней сборки — первая строка таблицы в «История git».
3. Только если правка их касается: почему сделано так — `docs/adr/`; что значат слова — `CONTEXT.md`;
   что именно просили — `manifest.md` в папке сборки (указана в начале `PROGRESS.md`).

После правки:
- коммит — по правилам из «История git»;
- строка в «Правки без автопилота» в `PROGRESS.md`: дата — что — почему;
- починенный пункт из «Не доделано» или «Известные баги» — удали;
- договорились с пользователем о том, что следующая сборка не должна пересматривать, —
  строка в «Договорились», его словами.

### История git

Целиком не читай — бери срез под вопрос:

| Вопрос | Команда |
|---|---|
| что правили после последней сборки | `git log --oneline "$(git log -1 --format=%h --grep='^chore(autopilot): build landed')"..HEAD -- . ':(exclude).autopilot'` |
| всё, что делали ради требования | `git log --oneline --grep="R02"` |
| история файла | `git log --oneline -10 -- <файл>` |
| когда появился или исчез код | `git log --oneline -S "<фрагмент>"` |
| почему строка такая | `git blame -L <с>,<по> <файл>`, затем `git show <sha>` |
| что внутри коммита | `git show --stat <sha>` |

Срез длиннее ~30 коммитов — отдай его субагенту и возьми выжимку в десять строк.

Коммит: заголовок — что, коротко и по-английски (`fix: dates in one format`), без `Co-Authored-By`;
трейлер `--trailer "Requirements: R02"`, если правка касается требования из `manifest.md`.
Заголовок `chore(autopilot): build landed` пишет только автопилот — по нему находят последнюю сборку (коммиты здесь английские).
